# 选区捕获先有门禁：45 ms 里做四件事，且不能弄坏用户手上的东西

> 状态：`completed`
>
> 上游判据：[T-Gate 0 交接方案](../completed/2026-11-27-tauri-handover-t-gate-0.md) §5「选区与替换：原生必须先有自己的门禁」、§6「T-Gate 0 真正关闭还缺两件」的第 1 件
> 归属批次：Phase 1 收口（单实例之后、翻译迁移之前）
> 门禁：`python scripts/check-native-selection.py --exe <release exe>`（18 项）
> 数字来源：本机单屏 3840×2160 @125%（面板窗口）、Win11 26300、release 构建

## 1. 为什么先写门禁，不先写实现

`easyflowhub-app/src-tauri/src/launcher.rs` 里的 `capture_selected_text` 已经在产品里跑了几个月，语义是清楚的：按热键 → 记下前台窗口 → 记下剪贴板序列号 → 注入 `Ctrl+C` → 等序列号变 → 读文本 → 把剪贴板还回去。原生壳要照搬的不是这段代码，是它**承诺过的东西**：用户按下热键之后，他的剪贴板里还是他那张图，他的选区还在，而面板上已经出现了那段文字。

这段承诺里有四件事共享同一个预算：窗口要在 60 ms 内上屏（§7.1），捕获必须在这之前完成，否则面板先出现、文字后填，用户看到的是面板闪一下再长出内容。所以捕获不是"额外的活"，它是首帧路径上的一段——它慢 10 ms，首帧就慢 10 ms。

没有门禁的话，这段代码只能靠"看起来能跑"验收。而它涉及三样在单元测试里不存在的东西：**另一个进程**（前台窗口是谁）、**系统的剪贴板**（谁在用它、序列号动不动）、**真实的按键注入**（目标收不收得到）。这三样恰好是出错时最难从日志里看出来的部分。

## 2. 门禁怎么拿到一个真的选区

选区必须在一个**别的进程**里、在面板出现**之前**就已经是选中的。门禁用自己起的 `--note` 窗口当"用户的应用"：窗口里的 RichEdit 有一段 `sentinel` 文本，门禁点它、`Ctrl+A` 选中，然后按热键。这样被捕获的文本是门禁自己写进去的，长度、内容、编码都可断言。

顺带把"另一个程序占着剪贴板"做成被测场景：门禁起一个线程，把剪贴板打开并持有 200 ms，再按热键。这条不是刁难——它是 Windows 上真实发生的事（资源管理器复制文件时就会），而天真的实现会在这里阻塞到超时。

## 3. 四个不显然的决定

**`SWP_SHOWWINDOW` 而不是先 `focus()`。** 捕获要求目标窗口是**前台**窗口（`Ctrl+C` 只对前台窗口的焦点有效），但不要求它持有**键盘焦点**——恰恰相反，如果捕获时把焦点移到面板上，注入的 `Ctrl+C` 会打在面板自己的搜索框里，日志指纹是 `reason=self`。所以上屏用 `SetWindowPos(..., SWP_SHOWWINDOW)`：窗口在屏幕上、可拍照，焦点留在原应用。

**轮询序列号，不 `sleep(50)`。** 固定等待要么不够（慢机器上真的没复制完）要么白等（本机实测 14.9 ms 就完成了，剩下 45 ms 是纯浪费）。`GetClipboardSequenceNumber` 每 1 ms 读一次，读到变化就走。

**`CAPTURE_BUDGET = 45 ms`。** 60 ms 首帧预算，捕获必须留出上屏和绘制的时间。45 是 60 的 75%，正好是 Tauri 版量出来的那份等待的等价物。

**序列号没动就**不**清理剪贴板。** Tauri 版在失败路径上会 `empty()`，这在产品里是个真实的数据破坏：用户按 `Ctrl+Alt+Space` 想搜东西，而当时没有选区——`Ctrl+C` 没被目标接受，序列号不动，然后剪贴板被清空。他刚截的图没了。所以 `Prior::Other`（不是我们写的文本）在这里**什么都不做**，只记一条 `prior=other restored=false`。

## 4. 门禁逼出来的真缺陷：修饰键还按着，注入的是裸 `c`

第一次跑门禁，首轮捕获是 `reason=no_copy`，而且笔记窗口的文本从 43 个字变成了 **1 个字**（`text_len=1`、`title="c"`）。

这个症状看起来和"没复制"毫无关系，但两件事是同一个原因。`WM_HOTKEY` 在组合键**物理按住**时就被投递——Windows 不等用户松手。而按键注入的修饰键状态来自 `SendInput` 自带的 `KEYEVENTF` 序列，注入的 `Ctrl` 是"按下-松开"一次性的，**系统记录的物理状态仍然是按下**。于是：

1. `Ctrl+C` 注入后，目标收到的是 `c` —— 因为注入的 `Ctrl` up 已经把它解掉了；
2. `c` 是一个**字符**，直接打进笔记的选区，把它覆盖成 1 个字；
3. 文本插入不动剪贴板序列号，所以日志里只有"序列号没变"，读起来完全像"复制没发生"。

**修法是等修饰键真的松开**，上限 12 ms，计入同一个 45 ms 预算：

```rust
fn wait_for_modifiers() -> Duration {
    let at = Instant::now();
    while at.elapsed() < MODIFIER_RELEASE {
        let down = [VK_CONTROL, VK_MENU, VK_SHIFT]
            .iter()
            .any(|vk| unsafe { GetAsyncKeyState(*vk as i32) } as u16 & 0x8000 != 0);
        if !down { break; }
        std::thread::sleep(Duration::from_millis(1));
    }
    at.elapsed()
}
```

用 `GetAsyncKeyState` 而不是 `GetKeyState`：后者回答的是**调用线程的消息队列**里的状态，而热键线程的队列里那对 key-up 可能还没被处理——正是我们要等的东西，却读不到。本机实测 `held_ms=1.13`，即修饰键在 1 ms 内就物理松开了，12 ms 上限只是兜底。

`replace()` 也要等：粘贴的 `v` 被同一个原因打成裸 `v`，会把译文换成字母 `v`。

**这条只有真按键注入才复现。** 单测里没有物理键盘，`GetAsyncKeyState` 回答不了；门禁是唯一能按住 `Ctrl+Alt` 然后注入的地方。所以它成了 §5 那条"先写门禁"的第一个证据。

## 6. 没做的

- **`Alt` 组合与 `Shift+Insert` 兜底**。有些目标（终端、部分 Electron）对 `Ctrl+C` 的响应是"复制到 kill ring"而不是剪贴板。Tauri 版也没做，这里保持一致，等真遇到再加。
- **UIA / `WM_GETTEXT` 直读**。`Ctrl+C` 改的是用户剪贴板，是侵入式的；`TextPattern` 能不改剪贴板拿到选区。但 UIA 对每一类目标都是一套新的等待与失败模式，而 Tauri 版用剪贴板已经跑通了——迁移阶段不引入第二套语义。
- **多显示器下的坐标**。捕获不在乎坐标，但门禁的面板定位在乎；本机单屏，`--scale` 只证明数学。
