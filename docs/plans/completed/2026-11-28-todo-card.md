# 待办卡片：原生窗口，可勾选、可编辑，证据在数据库与像素上

`create_todo_card_window` 在接管态下一直回一句「已由原生壳接管」。这一批把那个窗口做出来：
一个 320×400 的桌面浮卡，读 `notes.db` 里的 Markdown checkbox 行，**勾选会写回正文**，
点击文本能就地编辑，Esc 关闭而进程留下（托盘还在）。Tauri 命令的转发在
[manager-new-note](./2026-11-28-manager-new-note.md) 里接上。

- 状态：`completed`（2026-11-28）
- 门禁：`scripts/check-native-todo-card.py` **17/17**
- 单测：原生 `cargo test --locked --workspace` **335**（新增 18：`hub-core::todo` 11、`hub-ui::todocard` 6、`args` 1）
- 入口：托盘菜单「待办卡片」、`--todo-card`

## 1. 为什么规则先落 `hub-core`

待办不是表：产品把它存成笔记正文里的 `- [ ]` 行，权威解析器是前端的
`easyflowhub-app/src/lib/todoParser.ts`。原生这边若各写一份"看起来像待办"的判断，
第一次遇到 `1. [ ]`、缩进或 `* [x]` 就会分叉，而症状是"我的待办在卡片里消失了"，
会被算在卡片头上。

所以 `hub-core/src/todo.rs` 逐条抄了前端语法（缩进、`-`/`*`/数字标记、`[x]`/`[X]`、
尾部 `@done:`），并带 11 个单测钉住：勾选写入 `@done:<ISO>`、取消时整段移除、
改文本保留标记与时间戳、空文本拒绝而不是抹掉任务、`@done:` 粘在词里不算时间戳。

写入用**文本定位**而不是行号（前端 F05 的 `locateTodoLine`）：卡片读到的行号是快照，
另一个窗口在上面插一行之后，直接按旧行号改写会打中上一条任务。`Locate::{Exact, Relocated,
Conflict, Missing}` 里 `Conflict` 是刻意的拒绝——同名两条时宁可不动，也不猜。

## 2. 为什么工具条是纯函数

32 逻辑像素高的条上要放计数与 `+ ↻ 图钉 ×`。若只写成连续的 `ui` 调用，重叠只能靠截图吵架。
`hub_ui::todocard::strip_layout(width)` 返回五个矩形加一个拖动区，三个宽度的单测断言
两两不相交、都在条内、顺序与绘制顺序一致；`MIN_WIDTH = 220` 是拖动区不再塌陷的下限，
窗口的最小宽度就用它。

命中矩形同理：每帧把每行的 checkbox 与文本矩形交给 `app`，由它乘缩放写进日志
（`todocard_hit note=… line=… x=… y=… w=… h=…`），门禁在**卡片报告的坐标**上真点。
这和快速笔记的 `island_rect` 是同一个契约：日志说布局，门禁按布局按键。

## 3. 窗口与生命周期

- **单例、immediate viewport**，与工作台同构：无岛、无跨帧状态，deferred 只会多一帧延迟。
  `Option<Shell>`，关闭即 `None`；再次打开是新的读库，不是唤醒旧列表。
- **`settle` 认识卡片**：既有的"0 笔记就结算"在 `--resident --todo-card` 下会立刻退进程，
  把刚开的卡片一起带走。现在卡片开着时 `hub_idle` 只记一行。
- **拖动**沿用快速笔记的做法：每帧按屏幕光标位移搬窗（`ViewportCommand::StartDrag` 在此环境不搬窗，
  记录见 `note/drag.rs`）。
- **固定到桌面**走 `hub_win::window::attach_to_desktop(hwnd, on)`：`GWLP_HWNDPARENT = Progman`，
  写完 `SWP_FRAMECHANGED` 重算非客户区；顺序与 Tauri 版一致——固定先挂父窗口并取消 topmost，
  取消固定再恢复 topmost。
- **刷新**：打开时一次，之后每 30 s 一次（前端轮询同频），写操作后立刻 reload。

## 4. 门禁怎么判

`check-native-todo-card.py` 复制 live schema 后把行换成本轮的种子：待办箱
`- [ ] 买菜 / - [x] 倒垃圾 / - [ ] 交电费`，项目笔记两行。然后断言：

1. `todocard_reload groups=2 open=3 done=2`——解析与分组对；
2. 客户区 `480×600`（320×400 @150%），无边框；
3. 五条待办各有命中矩形；
4. **未完成在前**：卡片顺序是 `0, 2, 1`，中间那条已完成被排到最后（种子故意把它放中间，
   只回显正文顺序的实现过不了）；
5. 真点 checkbox → `todocard_toggle … done=true created=false`，库首行变
   `- [x] 买菜 @done:2026-…`；
6. **文字区域的亮像素 230 → 0**：完成行的文字用 `ink_disabled`，这条证明"画面上也变了"；
7. **checkbox 中心像素 `(33,37,45) → (40,49,62)`**：勾选态换了填充；
8. 再点一次 → 库首行**逐字节等于** `- [ ] 买菜`；
9. 点文本 → 全选 → 输入 → Enter → `todocard_commit id=proj line=1 created=false`，库中该行
   `- [ ] gate-ok`（标记与状态都留着）；
10. Esc 关窗，窗口消失，进程仍活；
11. 托盘 `WM_COMMAND(MENU_TODO_CARD=4)` → 卡片重开，且有一条新的 `todocard_reload`
    （证明托盘入口真的接上了，不是只有命令行）。

## 5. 两个把门禁写错的坑

- **`save_note_body` 的返回值是"是否新建"，不是"是否成功"**。第一版把 `Ok(false)` 当失败，
  日志写成 `ok=false`，门禁跟着判红——但数据库其实已经写对了。现在日志打
  `created=true|false`，失败单独打 `error="…"`。一个布尔值承担两种含义，就会在门禁里
  制造一次假失败。
- **勾选会让行移动**。行从"未完成"区跳到"已完成"区，原来那个 y 坐标被下一条占据：
  第一次跑门禁时"第二次点击取消勾选"实际点到了下一条任务（日志 `line=2`），像素采样也取了
  别人的文字。现在每次点击前后都用卡片**最新报告**的矩形（`wait_hit`）。
  这同时说明卡片的行为是对的——它真的把完成项移下去了。
