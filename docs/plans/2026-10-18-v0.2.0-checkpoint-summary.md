## Windows sidecar 打包修复（2026-10-18）

- 原构建脚本只比较 `cmd/scriptmgr/main.go`，会漏掉 relay 等内部包的更新；本轮发现 Go 源码已比 `scriptmgr.exe` 新，但旧时间戳判断仍报告 up-to-date。
- 原 Tauri 配置没有声明 `scriptmgr.exe` 资源，之前生成的 NSIS / MSI 因而不含 sidecar。新增资源映射后，Tauri 将文件放在发布输出根目录，匹配运行时先查找应用 exe 同目录的逻辑。
- 新构建输出、portable 输出、NSIS 文件清单与 MSI CAB 中均验证到同一 sidecar；源文件与 portable/MSI payload 的 SHA-256 一致。portable app 进程保持运行 5 秒后由本轮检查正常关闭。
- Release workflow 现在在 Windows app 构建步骤安装 Go，并检查 Tauri 输出 sidecar 哈希；单独上传的 sidecar 通过 `GOOS=windows GOARCH=amd64 CGO_ENABLED=0` 构建，避免 Ubuntu ELF 文件带 `.exe` 后缀。工作流本身尚未在 GitHub 执行。

## Relay / 管理 API 安全边界（2026-10-18）

- ScriptMgr 管理 API 只接受 loopback IP（`127.0.0.0/8` 或 `::1`）；通配地址和远程网卡地址会被拒绝。Relay 默认绑定 `127.0.0.1`。
- Tauri 开发/打包来源采用白名单，未知浏览器来源返回 `403`，无 `Origin` 的 CLI 调用保持可用。
- Relay 配置快照、provider 快照、扩展清单和有效贡献对外脱敏 `api_key`、已知认证类 header 与含凭据的 `base_url`；用未修改的占位值保存时保留旧值，清空/删除密钥会清除。header 脱敏按名称启发式匹配，无法保证覆盖所有自定义凭据名。
- 已补管理 API 非 loopback 地址拒绝测试，以及配置 PUT 响应不含密钥断言；聚焦 / 全量 Go 测试与前端 39/285 项、TypeScript、`git diff --check` 通过。此项关闭了无认证远程监听与已知敏感配置回显问题。
- 剩余安全边界：旧版 `api_key` 仍可明文存储在本地 JSON；CORS 不阻止同机进程访问 loopback；未知命名的自定义认证 header 可能不匹配脱敏启发式。密钥环境变量配置与真实 Provider 测试仍在发布验收清单中。

## 录音后语音转文字切片（2026-10-19）

- 设计基线 [ADR-0008](../decisions/ADR-0008-voice-transcription-and-relay.md)：native owner 为新增 `transcription.rs`，首个 Provider 复用本机 Relay 的 OpenAI 兼容 `POST /v1/audio/transcriptions`（multipart：`file`、`model`、可选 `language`）；请求经 `TranscriptionTransport` trait 抽象，fake transport 覆盖单元测试，未来本地模型 / CLI Provider 实现同一 trait 接入。
- 边界：音频字节不进入 WebView（在 native 侧读取并 multipart 发送）；25 MB 上限（约 4.5 分钟 WAV）、180 秒请求截止、响应只接受 `text` 字段且为空视为失败；错误分类为固定中文文案，不回显原始 Provider 响应体。密钥、路由与 failover 仍归 `scriptmgr-go/internal/relay`，EasyFlowHub 不存储凭据，设置只保存 `model` / `language` 偏好。
- 隐私确认：任何音频离开本机前，界面显示文件名、大小、估算时长、目标 Provider（本机 Relay）与模型及隐私说明；未确认不发送、确认状态不跨会话持久化、重新转写同事务替换旧 transcript 附件。
- 数据模型：`inbox_attachments.kind` additive 增加 `transcript`（沿用 audio 的 CHECK 重建迁移）；transcript 文本附件遵循附件即事实源约定；`convert_inbox_item_to_note` 对 transcript 附件把文本嵌入笔记正文；`get_transcript` 提供有界读取（1 MB）供面板恢复已转写状态。
- 前端：`lib/tauri/transcription.ts` typed bridge、共享 `TranscribeControl`（复制文本 / 整理为笔记 / 重新转写）、Voice 面板 saved 状态与 Inbox 面板含音频附件项目挂载、设置页「转写」段。
- 验证：Rust 65 项 library tests（含 8 项转写聚焦测试）、前端 41 个文件 / 299 项、TypeScript、Vite 生产构建、主题 token 审计、`cargo check`、Go tests、`git diff --check` 通过。
- 待人工验收：Windows 打包态麦克风 smoke、真实 Provider 至少一次成功转写、重新打开 Manager 后 transcript 仍可读取；实时转写、说话人识别、本地模型适配器与自动转写明确不在本切片。

## 仍需人工验收

当前 CUA 环境没有可控制的原生应用窗口，因此以下证据不能由本轮自动化替代：

1. Launcher 中键、焦点、拖动、Esc、排除软件和鼠标中心定位。
2. Snow Shot D 盘安装、MCP 开关和截图会话。
3. 真实 Relay Provider、不同编辑器选区替换和打包态剪贴板读写。
4. Files 回收站/权限/锁定/长路径。
5. Downloads 公开资源成功、取消、重试、冲突和权限。
6. 明暗主题、高对比度和关闭透明效果下的实际可读性。
7. Voice (P2) 麦克风权限、设备占用、WAV 播放、`.part` 保留和 Inbox 回流；转写需真实 Provider 至少一次成功、重新打开 Manager 后 transcript 仍可读取、Relay 未启动 / 模型未配置 / Provider 不支持转写接口时有可理解失败且音频原件不受影响。只有当 Voice 纳入本次 RC 时才是发布阻塞项，否则 Phase 5 保持 `in_progress` 并延后收口。

P0/P1 核心 RC 需完成第 1–6 项并回填 [windows-package-smoke.md](../checklists/windows-package-smoke.md) 与主题 checklist；不纳入 RC 的 Voice 不阻塞核心发布，但 Phase 5 继续保持 `in_progress`。如果 RC 包含 Voice，第 7 项也必须通过后才能发布该能力。
