# 2026-11-24 Native Runtime 重构设计（Windows 原生单进程）

- status: accepted（2026-11-24 两轮确认完成，9 项决策已定；待 Phase 0 的 G0 验证后进入实施）
- related ADR: [../decisions/ADR-0009-windows-native-runtime.md](../decisions/ADR-0009-windows-native-runtime.md)
- 影响范围：`easyflowhub-app/src`（UI 重写）、`easyflowhub-app/src-tauri/src`（壳迁移）、`scriptmgr-go`（保留为 worker）
- 度量工具：`scripts/measure-footprint.ps1`（内存/磁盘）、`scripts/measure-latency.ps1`（响应，主门禁）

## 1. 一句话结论

把"WebView 桌面壳"换成 **单进程原生 Rust 壳 + egui 页面 + 系统 RichEdit 文本岛**；但不是把现有 13 个面板整体翻译一遍——先按"常驻 / 按需 / 可丢弃"重划需求，v2 只原生实现高频面（Launcher、快速笔记、待办、笔记、脚本、设置、回收站），低频面（文件、下载、语音、relay、MCP、扩展）退为按需 worker + 最小入口。UI 走"实色分层 + 主题 token + 克制动效"，并为软件渲染 / 远程桌面提供 `lite` 降级（集显默认走 standard）。

## 2. 先把"占用大"拆成三种成本

"占用"不是单一指标。三种成本混在一起讨论，会做出错误的技术选择：

| 成本 | 当前形态 | 用户感受 | 正确的解法 |
|---|---|---|---|
| 常驻成本 | 托盘状态也保留 manager + launcher 两套 webview | 开机后什么都不做就吃掉几百 MB | 常驻部分必须原生、必须单进程 |
| 唤起成本 | 热键 → 窗口显示 → webview 首帧 | 按快捷键后"等一下才出来" | 预创建原生窗口 + 直接绘制，不经过 JS 启动 |
| 工作台成本 | Manager 打开后 13 个面板与 React 树 | 用久了越来越卡 | 允许它贵，但只在打开时贵；面板懒加载 |

因此验收指标必须分姿态测量，而不是只报一个"总内存"。

### 2.1 已确认的静态事实（2026-11-24 实测）

| 项 | 数值 |
|---|---|
| 安装目录 | 39.4 MB |
| `easyflowhub.exe` | 22.8 MB |
| `scriptmgr.exe` | 16.6 MB |
| WebView2 用户数据（profile） | 55.5 MB（启动后实测；每次启动约增长 2 MB） |
| 系统 WebView2 Runtime | 2029.3 MB（v158，系统共享，不计入本产品安装体积）。**2026-10 记录为 878.7 MB / v157，一个月内随版本翻倍**——这是"运行时绑定"的长期成本，虽然不在安装包里，但确实占用户磁盘 |

结论：**磁盘不是主要矛盾**。`easyflowhub.exe` 22.8 MB 里包含前端静态资源与 Rust 壳；换成原生后预计 12–18 MB，但这不是用户抱怨的重点。

**关于"高像素是否导致占用偏高"的校准（避免误判动因）：** 现状占用的大头是**每个窗口一套 renderer 的基线**（Chromium 进程本身、V8 堆、IPC、共享内存池），像素相关的纹理只是叠加项——一个 440×860 的面板缓冲在 150% 下只有 3.4 MB，即使乘以几个窗口也不足以解释"偏高"。所以：**高 DPI 优化救不了现状，但决定了原生方案的预算**——在新架构里，图集与首帧缓冲是常驻内存的主要构成之一（§7.2），也因此是"能不能在 4K@150% 下守住 60 ms + 体面内存"的关键。两件事不要混为一谈：现状要换运行时，新架构要按像素算账。

**开发/验证机画像（2026-11-24 实测，作为唯一测量环境）：**

| 项 | 数值 | 对设计的影响 |
|---|---|---|
| CPU | AMD Ryzen 7 4800H（8 核） | — |
| RAM | 31.4 GB 可用 | 进一步确认内存不是可用性瓶颈，也解释了"8 GB 也够"的判断 |
| GPU | Radeon 集显（AdapterRAM 512 MB 报告值，实为共享内存） | 集显是标准环境，不是边缘环境 |
| 分辨率 / 缩放 | 3840×2160 @ **150%**（逻辑 2560×1440，工作区 3840×2088，单显示器） | **关键**：字体栅格化面积 ×2.25，首帧纹理按物理像素计；设计的估算必须按这个环境校准，不能沿用 1366×768 |
| 显示器数量与缩放档 | 当前 1 台 @150% | 决定图集/纹理需要保留几档缓存。**接副屏或开启 Parsec 虚拟显示后会变成 2 个缩放档**，缓存档数上限（2 档）就是按这个上限设计的 |
| OS | Windows 11 Pro for Workstations build 26300 | 高于文档假设的 24H2，Win10 覆盖只能靠发布前 checklist |
| 虚拟显示 | 存在 Parsec Virtual Display Adapter（当前未运行） | 串流/虚拟显示下渲染路径不同，**其测量结果不作为基线** |

### 2.2 姿态基线（首个姿态已实测，2026-11-24）

**姿态 A：托盘静置**（两个窗口均 `visible: false`，启动后静置 2 分钟，无人操作）：

| 指标 | 实测 | 构成 |
|---|---|---|
| 进程数 | 10 | host 1 + sidecar 1 + conhost 1 + WebView2 7 |
| **Private Bytes** | **545.3 MB** | WebView2 合计 ≈ 514 MB、host 10.6 MB、sidecar 19.3 MB |
| Working Set | 846.1 MB | |
| 最大单进程 | 352.9 MB | 单个 `msedgewebview2.exe`（renderer） |
| WebView2 profile（磁盘） | 55.5 MB | 启动一次增长 ~2 MB |

两次采样（启动后 30 s 与 130 s）分别为 564 MB / 546 MB，说明这是**稳态**而非启动瞬时峰值。

这条数据把动因从判断变成了证据：**没有任何可见窗口、没有人操作，常驻仍是 545 MB**——是原生方案 65 MB 解释线的 **8.4 倍**。也就是说占用的来源不是"用户在用它"，而是"两个隐藏窗口各有一套 renderer"。

#### 2.2.1 三姿态实测与 P0.5 前后对比（2026-11-24）

三姿态由 `scripts/measure-footprint.ps1 -Label <pose> -Json -OutFile ...` 归档到 `docs/releases/footprint/0.2.0/`，每姿态静置后再采样。

**改造前**（Manager + Launcher 都在 `tauri.conf.json` 里预创建；本机 3840×2160 @150%）：

| Pose | 进程构成 | Private | Working Set | 备注 |
|---|---|---|---|---|
| `idle` | 1 host + 7 webview + 1 sidecar | **600.0 MB** | 895.1 MB | 静置 2 min，无可见窗口 |
| `launcher` | 同上 | 477.2 MB | 771.7 MB | 比 idle 还低：隐藏窗口的渲染器会被内存压力回收，单次快照不能当作"窗口成本" |
| `manager-2notes` | 1 host + 9 webview + 1 sidecar | 627.8 MB | 987.4 MB | 每多一个窗口约 +1 个 webview 进程 |

**改造后**（Manager 按需创建 + 关闭即销毁，见 [window-lifecycle-and-latency-contract.md](./2026-11-24-window-lifecycle-and-latency-contract.md) Batch B）：

| Pose | 进程构成 | Private | Working Set | 相对改造前 |
|---|---|---|---|---|
| `idle` | 1 host + 6 webview + 0 sidecar | **261.6 – 282.8 MB**（三次采样 261.6 / 274.9 / 282.8） | 431.3 – 474.1 MB | **−53% ~ −56%** |
| `idle` + Manager 隐藏但未销毁 | 1 host + 7 webview | 496.0 MB | 783.0 MB | 只隐藏不销毁等于没省——这是"关闭即销毁"的直接依据 |
| 2 个快速笔记 | 1 host + 8 webview | 447.6 MB | — | 每窗口 ≈ +1 进程 |
| 关闭全部笔记后 | 1 host + 6 webview | 346.6 MB | — | 窗口销毁后进程数回落 |
| 连续 15 次热唤起后（Manager 仍隐藏存在） | 1 host + 7 webview | 496.0 → 500.3 MB | — | 每次唤起无累积（+4.3 MB / 15 次） |

**结论**：(1) 动因判断成立——占用与"窗口是否被创建/销毁"相关，而不是与"用户是否在用"相关；(2) `idle` 降幅 53% 已远超 Batch B 的 25% 判定线，不触发"设计被证伪"分支；(3) `sidecar` 在静置时为 0 进程（懒启动），此前口径里的 19.3 MB 也随之下移。

**读数口径提醒**：WebView2 的 renderer 会按内存压力回收，同一姿态的两次快照可能相差 50–200 MB（本例 `launcher` 姿态反而低于 `idle`）。因此**跨姿态比较看进程数与趋势，绝对值只用于同版本前后对比**，且每次采样必须记录姿态定义与静置时长。

脚本按 `easyflowhub.exe → msedgewebview2.exe / scriptmgr.exe` 的父进程树汇总 Private Bytes，直接给出"窗口数 ↔ 进程数 ↔ 内存"的对应关系；同时**逐显示器**输出分辨率、缩放、工作区与主 GPU——**因为字体图集与首帧纹理随 DPI 与物理像素增长，不同 DPI 下的内存读数不可直接比较**。

> **必须按进程树统计，不能按进程名全局计数。** 本机全系统有 20–26 个 `msedgewebview2.exe`（其他应用的），按名字数会把占用放大 2–3 倍并得出"应用在泄漏"的错误结论。脚本从 `easyflowhub.exe` 向下遍历父进程关系，并输出 `TOTAL` 行；这一点在比较不同版本时尤其关键。

> **测量必须 DPI-aware。** 一个 DPI-unaware 的进程（PowerShell 5.1 默认如此）会看到虚拟化坐标：本机 3840×2160 @150% 会被报告成 2560×1440 @100%，物理像素与缩放同时被低估 1.5 倍。脚本已显式调用 `SetProcessDpiAwareness(PER_MONITOR_DPI_AWARE)`，并用 `GetDpiForMonitor(MDT_EFFECTIVE_DPI)` 取真实缩放；后来者改脚本时不要把这个调用去掉。

**测量范围：只在本机测（2026-11-24 用户确认）。** 不找第二台低配机、不做跨机对比——8 GB 机器上内存余量充足，"哪台机器更吃紧"没有决策价值。三姿态的目的是拿到**增长斜率**（窗口数 → 进程数 → 内存），证明"占用与是否在用无关、只与窗口数相关"这一结构判断；三组数字加起来 5 分钟就能采集完。

**真正需要精确的是延迟**（§7.1），它才决定架构是否成立；内存只需要一个可信的量级。

### 2.3 结构性判断（不依赖具体数值）

1. `tauri.conf.json` 中 manager 与 launcher 都是 `visible: false` 创建 → 启动即两套 renderer，托盘静置也不释放。
2. `create_note_window` / `create_todo_card_window` / widget 每调用一次就新建一个 `WebviewWindow` → 内存与窗口数线性相关，而不是与"是否在用"相关。
3. 一次脚本列表请求跨 WebView → Rust → HTTP → Go 三跳；Go sidecar 常驻 16.6 MB 可执行文件与独立进程。
4. 2026-10-22 白屏事故的三个根因（WebView2 profile 半写、`EBWebView` 损坏、cargo 增量未重新内嵌 `dist`）都源于"运行时 + 构建期资源内嵌"这套模型。

### 2.4 附带发现：开机自启动失效（2026-11-24 实测）

用户反馈"自启动设置在本机未生效"。检查结论如下。

**已确认的事实：**

| 检查项 | 结果 | 含义 |
|---|---|---|
| `HKCU\...\CurrentVersion\Run` 的 10 个值 | **无 EasyFlowHub** | 实际不存在启动项 |
| `...\Explorer\StartupApproved\Run` | 有 `EasyFlowHub`，首字节 `02` | Windows 仍留有"曾被批准/启用"的记录 → 该项**创建过**，后来被移除 |
| `notes.db` 的 `settings` 表 | 只有 quick_note / trash / editor / launcher_trigger / todo / translation / transcription / developer | **应用没有持久化自启动偏好** |
| `capabilities/default.json` | `autostart:allow-enable/disable/is-enabled` 齐全 | 不是权限问题 |
| `nsis/installer-hooks.nsh` | 只 `taskkill`，不写注册表 | 安装钩子不直接删除该项 |

**根因（设计层面，已确证）**：自启动的**唯一状态来源是注册表项**。`useAutostartSettings.ts` 挂载时用 `isEnabled()` 读状态、切换时直接 `enable()` / `disable()`，没有把偏好写进 `settings` 表。因此注册表项一旦被外部清除（更新/重装、清理工具、profile 迁移等），应用既不知道它曾经开启过，也无法恢复——UI 静默回到 OFF，表现为"设置没生效"。

**尚未确证**：具体是谁删除了该项。`app.log` 只在 debug 模式落盘且已被本次会话重置，缺少历史证据。这不影响修复方案——方案对"任何外部删除"都成立。

**修复（建议随 Phase 0.5 一起做，属独立小改动）：**

1. **持久化偏好**：`settings` 表新增 `autostart = {"enabled": bool}`。UI 状态以持久化为准，注册表只是执行结果。
2. **启动对账**：若持久化为 `true` 而 `is_enabled()` 为 `false` → 重新 `enable()`；失败只记录并提示，不阻塞启动。这是让"被外部删掉"能自愈的唯一办法。
3. **写入后校验**：`enable()` 之后立刻 `is_enabled()` 复核，失败要把错误暴露到界面。现在只有一个 `console.error`，用户永远看不到失败。
4. **顺带修单实例回调**：`tauri_plugin_single_instance::init` 的回调忽略 `argv`，开机自启时若已有实例在运行会**弹出 Manager**，而不是静默唤醒。应改为：带 `--autostart` 时只唤醒常驻、不显示窗口。

> 这条与运行时重构正交，但 v2 重写常驻壳后**会以同样形式复现**（新壳同样只有一个注册表项）。所以正确做法是：旧版按上面 1–4 修掉，新壳从第一天就按"持久化 + 对账"实现，并在 G1 门禁里加一项"删除启动项后重启能自愈"的验证。

**落地状态（2026-11-24 已实现并实测）**

| 步骤 | 实现位置 | 行为 |
|---|---|---|
| ① 持久化偏好 | `src-tauri/src/autostart.rs` + `settings::read/write_setting_json` | `settings` 表新增键 `autostart = {"enabled": bool}`；**故意不放进 `AppSettings`**，因为设置面板的全量 `update_settings` 用旧快照保存会覆盖它 |
| ② 启动对账 | `autostart::reconcile()`，`lib.rs` setup 内调用 | 意图 `true` + 系统缺失 → 补回，`repaired=true` 并写 `logging`；首次升级无意图时按当前系统状态迁移，不写注册表 |
| ③ 写入后校验 | `autostart::apply()` | `enable/disable` 后立刻回读；不一致返回错误（写入成功不等于生效），并把注册表回滚到改前状态，避免"半切换" |
| ④ 单实例回调 | `lib.rs` | `argv` 含 `--autostart` 时直接返回，不再把 Manager 抢到前台 |

前端不再直接调用 `@tauri-apps/plugin-autostart`：`useAutostartSettings` 走 `get/set_autostart_state` 两个命令，返回 `{system_enabled, user_enabled, repaired, available}`。`available=false` 时 UI 显示"无法读取"并禁用开关，而不是显示成"用户自己关掉了"；写入失败在面板内以 `role="alert"` 显示。

**新增一条对账边界（实测后补）**：意图为 `false` 而系统启动项存在时**不自动关闭**。该项可能被安装器或用户重新添加，每次启动强行关闭会与用户操作互相打架；UI 显示真实系统状态，让用户自己决定。

**实测记录（本机，dev 构建 + WebView2 CDP）**
- 首次启动迁移：`autostart` 键写入 `{"enabled":true}`，时间戳与进程启动同秒。
- 自愈：手动删除 `HKCU\...\Run\EasyFlowHub` → 重启应用 → 注册表值被自动补回（值指向当前 exe + `--autostart`），`StartupApproved` 同时写回 `02`。
- 开关链路：`set_autostart_state(false)` → `system_enabled=false` 且注册表值消失；再 `true` → 恢复，`available=true`。

> 注意：dev 构建的 `enable()` 写的是 `target\debug\easyflowhub.exe`。开发机测完要把启动项手动改回安装路径，否则开机会启动调试版。

## 3. 从需求重新推导

### 3.1 三条产品公理

- **A1 常驻必须便宜**：托盘常驻的每一个 100 MB，都会换来一次卸载。
- **A2 唤起必须即时**：热键是肌肉记忆。60 ms 内是"即时"，超过 60 ms 会被感知为"慢半拍"，150 ms 已是明确卡顿。**用户已明确这一条优先于 A1**——允许为响应多付内存，不允许为省内存牺牲响应。
- **A3 编辑必须可靠**：中文输入法、撤销、选区、复制粘贴任何一项出问题，都比"慢"更致命。

A2 优先于 A1 是本设计的排序前提，它直接决定了"预创建 + 常驻字体图集"这类取舍（§5.8）。A3 是技术选型的真正约束，也是"全自绘 UI"最大的风险点。

### 3.2 能力分档（决定谁进主进程、谁进 worker、谁不做）

| 档 | 能力 | 使用频率 | 目标形态 | 内存预算 |
|---|---|---|---|---|
| T0 常驻 | 托盘、全局热键、鼠标中键、单实例、设置读取 | 每次开机 | 主进程，无窗口 | ≤ 30 MB（无预热） |
| T0+ 预热 | 预创建的 Launcher（隐藏）+ 字体图集 + 首帧纹理 | 常驻全程 | 主进程，隐藏窗口 | 合计 ≤ 65 MB（standard）/ ≤ 55 MB（lite） |
| T1 高频窗口 | Launcher、快速笔记、待办卡片 | 每天多次 | 主进程，窗口预创建/复用 | 单窗口 +25 MB 内 |
| T2 工作台 | Manager：笔记、收集箱、待办、脚本、设置、回收站 | 每天 1–2 次 | 主进程，页面懒加载 | ≤ 220 MB |
| T3 低频能力 | 文件搜索、下载队列、语音/转写、relay、MCP、扩展、任务 | 每周或更少 | 独立 worker 进程，空闲退出；UI 只保留入口与状态 | 不进入常驻基线 |
| T4 不做 | 跨平台、云同步、账号、任意代码插件 | — | 明确排除 | — |

这个分档直接回答"重构到什么程度"：**T0–T2 原生，T3 保留 Go worker，T4 不做。**

### 3.3 v2 需求收窄（这是"从需求重新考虑"的核心）

现状 Manager 有 13 个模块。按代码量与使用频率做取舍：

| 面板 | 非测试行数 | v2 处置 |
|---|---:|---|
| notes（笔记/收集箱） | 2,004 | 原生重写（核心） |
| settings | 2,045 | 原生重写（含快捷键、外观、模块开关） |
| scripts | 1,753 | 原生重写（列表/执行/输出/运行记录） |
| trash | 510 | 原生重写 |
| todos | 428 | 原生重写（聚合视图） |
| files | 733 | 降级：worker + 最小入口（打开系统搜索/Everything 或简表） |
| relay | 741 | 降级：worker + 配置只读/简表单 |
| extensions | 662 | 降级为只读清单，v2 不做安装/热重载 |
| tasks | 475 | 合并进 scripts 的"运行记录" |
| downloads | 398 | 降级：worker + 队列简表 |
| mcp | 323 | 降级：worker + 状态页 |
| voice | 121 + hooks | 延后（v0.2 已标实验） |

结论：v2 原生范围约 **7k 行 UI 等价物**，而不是 23k 行全量。低频能力继续由 Go worker 提供能力，UI 用最小页面呈现状态。

### 3.4 非目标（写清楚，避免迁移期膨胀）

- 不追求像素级复刻：允许字体渲染、阴影、动画曲线有差异，但布局、层级、对比度必须一致。
- 不在迁移期改数据格式：`notes.db` schema 只加不改；不做"顺便重构"。
- 不同时重写 Go 脚本执行器：脚本发现/执行/MCP/relay 的 owner 不变。
- 不做插件 UI 沙箱：扩展仍是声明式 manifest。
- **不追求"更快"**：热唤起降到 60 ms 即停止加码（见 §5.8.1）。继续下探要靠更多预热，会拖慢冷启动并增加"预热数据过期"类难复现缺陷——那与"灵感稍纵即逝"的初衷相反。
- **不预热低频能力**：预热范围严格限定在 §5.8.1 的 P0/P1 档；P2 能力即使单次打开偏慢也不用常驻内存去换。
- **Launcher 不与工作台合并**：它是光标处的竖版动作面板（Quicker 式），不做全屏遮罩、不在面板里嵌工作台页面。合流会同时放大首帧缓冲（3.4 MB → 33 MB）与唤起延迟。

### 3.5 目标环境画像与降级策略（2026-11-24 修正）

原设计把 4 GB 机器当作目标画像。用户指出：可接触到的最低配置是 8 GB，4 GB 机器"运行 Win10 都勉强"，已不是现实目标。这个修正不只是改一个数字，它改变了 `lite` 存在的理由。

**最低支持配置：8 GB / 4 核 / 集显 / 1366×768 / Win10 22H2。** 但**设计与实测都按本机的 3840×2160 @150% 校准**（见 §2.1）——分辨率与 DPI 只是乘数，按大屏校准出的方案在小屏上必然成立，反之不成立。

- 4 GB 不再作为目标，也不承诺可用：允许启动，但不做性能承诺、不进 CI、不占预算。
- **集显是常态而非例外**（用户本机即为集显）。因此**集显必须跑 standard**，不能因为"集显"就降到 lite——否则主用户会一直在跑降级模式。
- 瓶颈也从"内存"转移：8 GB 下内存几乎不可能成为约束，真正的瓶颈是**集显填充率**与**远程桌面带宽**。

lite 定位因此改变：

| | 旧 | 新 |
|---|---|---|
| 存在的目的 | 救 4 GB 机器的命 | 应对渲染能力缺失或带宽受限 |
| 触发条件 | RAM 小 / 集显 / RDP | GL 初始化失败或回退软件渲染 / RDP 会话 / 用户强制 |
| 主要矛盾 | 内存 | **带宽与帧率**（RDP 重定向下每帧传输量） |
| 集显 | 进 lite | **留在 standard** |

降级策略：

- **渲染**：OpenGL（glow）为默认；集显同样走 standard，但 `elevation` 上限降为 1（不做大阴影），减少填充率浪费。初始化失败 → `lite`（软件渲染路径）。
- **窗口**：lite 下**仍预创建 Launcher**（响应仍是主门禁），但取消首帧纹理缓存与最近项预加载，用"少一点预热"换内存；快速笔记单实例。其余预热范围见 §5.8.1。
- **列表**：虚拟滚动 + 分页；>500 项不一次性布局；搜索走 SQLite FTS，不在内存里全量过滤。
- **预算**：standard 见 §7.2；lite 常驻 ≤ 55 MB（较前一版上调 10 MB——它不再服务 4 GB 机器，内存已非主要矛盾）、热唤起 ≤ 120 ms、RDP 下帧率 ≥ 20 fps。
- **可观测**：启动探测 GPU 能力与远程桌面标志 → `runtime_profile = standard | lite`；用户可强制覆盖。**不再探测 RAM 容量**，避免 8 GB 机器被误判降级。

这条修正也为 Phase 0 省了事：**不需要额外的低配机**。内存三姿态在本机采集即可；RDP 场景若要验证，用 `mstsc` 连本机回环，属可选项，不阻塞 G0。

## 4. 技术选型

### 4.1 候选矩阵

权重按用户确认的约束重排：编辑可靠性 25%、**集显适配与常驻成本 25%**、成熟度 20%、开发速度 15%、生态/维护 15%。**"视觉还原"不再计分**——UI 已改为简洁优先，网页视觉不再是目标。注意该项已从"内存"改为"常驻成本 + 集显可用性"：8 GB 下内存容量不再是主诉，这里区分方案的是"有没有 JS/多进程基线"和"能不能在集显上稳跑 60 fps"。

| 方案 | 编辑可靠性 | 集显/常驻 | 成熟度 | 开发速度 | 生态 | 结论 |
|---|---|---|---|---|---|---|
| Tauri + React（现状优化） | 5 | 1 | 5 | 5 | 5 | 多进程基线锁死，集显机与响应都无解 |
| **Rust egui + RichEdit 文本岛** | **4–5**（文本交给系统） | **5** | 4 | 3 | 4 | **采纳** |
| Rust egui 全自绘文本 | 3（自研 IME/选区） | 5 | 3 | 2 | 4 | 备选，风险高 |
| Rust Slint | 3（复杂文本证据少） | 5 | 3 | 3 | 2 | 备选 |
| C# WinUI 3 / WPF | 5 | 3 | 5 | 4 | 4 | G0 失败时的成熟退路 |
| Go + Fyne/Walk | 2 | 3 | 3 | 2 | 2 | 排除 |
| 纯 Win32/D2D 全自绘 | 5（可用原生控件） | 5 | 5 | 1 | 2 | 只作为性能兜底 |

### 4.2 结论

- **外壳与常规页面：egui/eframe**。理由：即时模式对"多窗口、悬浮、自绘玻璃"最直接；`ViewportBuilder` 支持透明/无边框/置顶/跳过任务栏；输入事件与 IME 由 winit 转发；`egui_kittest` 可做截图快照测试；与现有 10.8k 行 Rust 壳同语言。
- **笔记正文：Win32 `RICHEDIT50W` 子窗口**。理由：A3 的三项（IME/撤销/选区）全部由系统实现；候选窗定位、右键菜单、高对比度、无障碍免费获得；自研文本引擎是 3–5 个月起步的坑。
- **不用 WebView2 承载任何常驻 UI**；Manager 也不再用 WebView。
- **成熟度说明**：RichEdit 是系统组件（长期随 Windows 维护），egui 有稳定发布与生产使用，二者都有"可替换"边界（编辑器可换 C# 控件、壳可换 WinUI 3）。不选 Slint 的原因不是它不好，而是"复杂文本编辑 + 中文 IME"缺少足够证据，不符合"成熟优先"。
- **低端适配**：渲染层薄封装（`hub-ui::backend` 可切 glow / 软件路径），`lite` 模式关闭一切非必要合成；预算按 8 GB + 集显校准，并覆盖 RDP 与软件渲染两条路径。
- **UI 简洁化的连带收益**：不再追求网页级视觉还原，egui 的主要短板（控件样式、字体渲染差异、动效表现力）被降权，主题系统负责"好看"，而不是靠重特效堆出来。

## 5. 目标架构

### 5.1 进程与窗口模型

```text
easyflowhub.exe (Rust, 单进程)
├─ hub-win      窗口/托盘/热键/钩子/DWM/单实例/自启动/更新
├─ hub-ui       egui 主题、组件、Launcher、QuickNote 壳、TodoCard、Manager
├─ hub-editor   RichEdit 文本岛 + Markdown 装饰 + 图片/预览
├─ hub-core     notes/inbox/todos/settings/store(fts)/search/download/voice
└─ hub-bridge   scriptmgr worker 的 HTTP 客户端（可选进程）
        └─ scriptmgr.exe (Go, 保持现状；空闲 60s 退出)
```

窗口策略：

| 窗口 | 创建时机 | 销毁时机 | 说明 |
|---|---|---|---|
| tray | 启动 | 退出 | 无窗口，仅消息循环 |
| launcher | **启动即预创建，隐藏**（`show=false`） | 退出时才销毁（关闭 = 隐藏） | 响应优先的必然结果：热唤起不承担窗口创建成本；隐藏态不请求重绘。**语义是"光标处的动作面板"（Quicker 式），不是工作台**；默认竖版 440×860 逻辑像素，出现在光标所在显示器上 |
| quick-note-N | 用户新建 | 用户关闭 | 每窗口一个 egui viewport，共享同一进程与 GPU 设备；关闭后保留 1 个"温"实例供下次秒开 |
| todo-card | 用户打开 | 用户关闭 | 透明 + `Progman` 父窗口实现"固定到桌面" |
| manager | 首次打开 | 用户关闭 | 页面懒加载；关闭即释放纹理 |

**Launcher 是"跟随光标的动作面板"，不是全屏遮罩，也不是工作台。** 这一条已按用户澄清（2026-11-24）落定，形态参考 Quicker 快速面板：竖版多列动作网格、出现在光标处、点击即消失；工作台（Manager）是另一个窗口、另一种入口，两者不共用窗口。

| 项 | launcher（动作面板） | manager（工作台） |
|---|---|---|
| 形态 | 竖版面板，默认 **440×860 逻辑像素**（实测现版 `tauri.conf.json` 即 440×860） | 大窗口，页面式 |
| 位置 | 光标所在显示器的光标处，向四周夹紧到工作区 | 常规窗口位置，记忆上次 |
| 生命周期 | 启动预创建，关闭=隐藏，退出才销毁 | 首次打开创建，关闭销毁 |
| 首帧要求 | 热唤起 p95 ≤ 60 ms | 首次打开 ≤ 400 ms，会话内二次进入 ≤ 40 ms |
| 首帧纹理 | 1 份面板缓冲（150% 下 ≈ 3.4 MB） | 不缓存首帧纹理，按需重建 |

尺寸用物理像素算才是真的：440×860 逻辑在 150% 下是 660×1290 ≈ 0.85 Mpx，一张 RGBA 3.4 MB；若为了"更好看"做成全屏透明遮罩（2560×1440 逻辑 @150% = 3840×2160），同一张缓冲变成 33 MB，并且额外走 DWM 透明合成路径。**所以"面板形态"同时是内存约束和延迟约束，不是审美偏好。**

`lite` 模式差异（**注意：预热策略不再因 lite 而取消**，这是响应优先的直接后果）：

| 项 | standard | lite |
|---|---|---|
| launcher | 启动预创建 + 预加载最近项 + 首帧纹理缓存 | 启动预创建，但**不预加载最近项、不做首帧纹理缓存**（省 ~15 MB，首帧多 20–40 ms） |
| 快速笔记 | 允许多实例，保留 1 个温实例 | 单实例复用 |
| 合成 | 允许轻阴影与淡入淡出 | 无阴影、无淡入，直接出现 |
| 字体图集 | 首屏字符集预栅格化（单 DPI 档） | 收窄到启动界面上必然出现的字符 |
| 列表 | 虚拟滚动 | 虚拟滚动 + 更小预取页 |
| 字体图集/预热代价 | ~20 MB | ~12 MB |

#### 5.1.1 光标锚定与高 DPI：内存与首帧的共同变量

用户反馈"高像素设备占用偏高"——这个判断在原生实现里比在 WebView 里更关键：**首帧缓冲与字形图集都按物理像素计，面积随缩放平方增长**，而它们在热路径上又不能省（省了就破 60 ms）。

先给结论式的数字（launcher 默认 440×860 逻辑）：

| 缩放 | 面板物理像素 | 单张 RGBA 缓冲 | 两缓冲（缓存帧 + 实时帧） | 首屏图集（300–800 字） |
|---|---|---|---|---|
| 100% | 440×860 = 0.38 Mpx | 1.5 MB | 3.0 MB | 1.5–3 MB |
| 125% | 550×1075 = 0.59 Mpx | 2.4 MB | 4.7 MB | 2.3–4.7 MB |
| **150%（本机）** | 660×1290 = 0.85 Mpx | **3.4 MB** | 6.8 MB | **3–6 MB** |
| 200% | 880×1720 = 1.51 Mpx | 6.1 MB | 12.1 MB | 6–12 MB |

**尺寸不是常量，要按工作区夹紧。** 440×860 在 150% 下（工作区 3840×2088）绰绰有余，但在最低支持的 1366×768 @100%（工作区约 1366×728）下，860 逻辑高度已经超出。规则是：`面板高 = min(860, 工作区高 - 24)`，内容区虚拟滚动；宽度同理夹到 `min(440, 工作区宽 - 24)`。夹紧后缓冲更小，所以这一条只会让内存和首帧更好，不会更差——但实现时若忘了夹紧，会出现"面板底部被任务栏吃掉"的可见缺陷。

**动作网格列数：固定 4 列，窄屏降为 3 列，两套布局在启动期算好。**（2026-11-24 确认）

- 不做"按可用宽度连续自适应"：列宽连续变化会让每格的纹理缓存与命中测试失效，每次夹紧都重排，等于把不可控的抖动放进热路径。
- 判据只有一条：夹紧后**列宽 < 96 逻辑像素**（4 列在 440 宽下约 100，减去内边距与间距后刚好通过）就切 3 列。阈值写死为常量，不在运行期用内容宽度反推。
- 两套布局的度量（列宽、行高、每页行数、可见项数）在启动期按当前工作区与缩放各算一次并缓存；`WM_DISPLAYCHANGE` / `WM_SETTINGCHANGE` 时重算。热键路径只读缓存，不重算。
- 列数变化会改变可见项数量，因此**滚动位置以"项索引"而非"像素偏移"保存**，跨列数恢复时才不会跳到错误位置。

这条同时是内存约束：布局一旦固定，首屏纹理与图集的尺寸在启动期就确定，不需要为"可能变宽"预留缓冲。

**优化手段（按收益排序，全部零延迟代价）：**

1. **缓冲只按面板尺寸分配，永不按屏幕尺寸分配。** 这是 3.4 MB 与 33 MB 的差别，也是"面板而非遮罩"的直接收益。
2. **图集只栅格化首屏字符集**，其余字符由 egui 按需增长（增长发生在输入时，不在首帧）。不做 3500 常用字预栅格化——150% 下那是 30 MB 起。
3. **缓存按缩放分键，最多保留 2 档**（当前档 + 上一档），跨屏来回移动不重复栅格化；超过 2 档按 LRU 淘汰。键值把缩放量化到 0.25，避免 1.375 这类小数造成的缓存击穿。
4. **图标矢量按需栅格化并按档缓存**，不为每档预渲染全套图标。
5. **关闭 MSAA、不做中间离屏 FBO、不做模糊**：面板本身是实色分层，这些只增加带宽不增加质量。

**延迟相关的三个坑（都会让 60 ms 破线，且难复现）：**

- **不要在热键回调里枚举显示器。** `EnumDisplayMonitors` 在混合 DPI 多屏下要遍历所有适配器；改为启动期缓存显示器布局（工作区 + 缩放 + DPI），在 `WM_DISPLAYCHANGE` / `WM_SETTINGCHANGE` 时失效重建。热键路径只做：`GetCursorPos` → 命中缓存 → 算位置 → `SetWindowPos`。
- **`pixels_per_point` 必须在 `show` 之前设好。** 否则会先出一帧错误缩放的界面（表现为"闪一下再变大"），这比慢 20 ms 更难受。顺序固定为：解析目标显示器 → 设 ppp 与窗口尺寸 → 显示 → 呈现。
- **DPI 变化时新旧图集要交接。** 跨屏或系统改缩放时，先建新档图集再切换，旧档保留到新档首帧完成，避免"文字空白一帧"。这也是"保留 2 档"的主要理由，不只是省时间。

**明确不做**：按最大屏尺寸预分配（浪费且无收益）、多档图集常驻（内存换不到延迟）、为每档预渲染图标（同上）、用 `Blur` 换"高级感"（§5.4 已禁用）。

### 5.2 crate 结构

```text
easyflowhub/native/
├─ Cargo.toml            # workspace
├─ crates/
│  ├─ hub-win/           # windows-rs: 窗口、DWM、托盘、热键、钩子、单实例、更新
│  ├─ hub-ui/            # egui 主题与视图；不直接调用 Win32
│  ├─ hub-editor/        # RichEdit 宿主与 markdown 装饰
│  ├─ hub-core/          # 领域服务 + SQLite（rusqlite），无 UI 依赖
│  └─ hub-bridge/        # scriptmgr worker 生命周期与 HTTP 契约
└─ app/                  # main.rs：装配根，只做 wiring
```

依赖方向：`app → hub-ui → hub-core`，`hub-ui` 与 `hub-win` 通过 trait 解耦（便于 `egui_kittest` 无窗口测试）。`hub-core` 不得依赖 `windows` crate。

### 5.3 数据与兼容

- 复用 `notes.db`：表结构、索引、FTS 配置、附件路径规则全部保持不变。
- 新增 `schema_meta` 之外不加迁移；需要新字段时先写"可空列 + 双读"，等 Tauri 版本下线后再收紧。
- 双栈期单写者：命名互斥量 `Global\EasyFlowHub.WriteLock`；抢不到写锁的进程以只读模式启动并提示。
- 升级/回滚：升级前自动 `VACUUM INTO` 备份 `notes.db.bak-<date>`；回滚 = 重装 Tauri 包读同一库。

### 5.4 视觉与主题：简洁优先，token 驱动

默认主题是"实色分层"，不是毛玻璃。四层足够表达层次：背景 → 表面 → 抬升表面 → 浮层，靠边框与明度差区分，不靠模糊与阴影堆叠。

| 层 | 用途 | 默认实现 | 说明 |
|---|---|---|---|
| 背景 | 窗口底色 | 实色 | 不使用透明与模糊 |
| 表面 | 卡片、列表容器 | 实色 + 1px 边框 | 边框对比度走 token |
| 抬升表面 | 选中项、悬停 | 表面亮度 +1 档 | 不使用发光 |
| 浮层 | 菜单、下拉、Toast | 实色 + 极轻阴影 | `lite` 下退化为 1px 边框 |

主题 token（六类，全部集中定义，页面禁止魔法值）：

- `color`：背景 / 表面 / 边框 / 文字（primary, secondary, disabled）/ 语义色（danger, success, warning）。
- `typography`：字号阶（12/13/14/16/20）、字重（400/500）、行高。
- `spacing`：4 的倍数阶（4/8/12/16/24/32）。
- `radius`：4/8/12，窗口圆角单独处理。
- `elevation`：0/1/2（0 = 无阴影；`lite` 强制 0，**集显 standard 上限 1**；2 仅在探测到独显且未开启省电时启用）。集显的限制不是"跑不动"，而是填充率要留给内容——阴影是最容易被滥用又最不值钱的开销。
- `motion`：`fast 90ms` / `normal 150ms` / `slow 220ms`，缓动统一 `ease-out`；用于面板进出、列表增删、焦点迁移。

特效策略：

- 默认关闭：毛玻璃、背景模糊、渐变、发光、视差。
- 可选主题：Win11 且用户显式开启时启用 Mica；Win10 自动实色。
- 尊重系统"减少动画"：关闭 `motion`，只保留即时状态切换。
- 动效只解释状态变化，不做装饰性循环动画（不占 CPU、不干扰输入）。

字体与渲染：

- 优先 `Microsoft YaHei UI` / `Segoe UI Variable`，通过系统字体文件加载，不内嵌大字体。
- 中文按需栅格化进图集；`lite` 降档。
- 允许与现版存在字重、字距差异；不允许层次、间距节奏、对比度（深色/浅色/高对比度）出问题。

### 5.5 平台集成

- 单实例：命名互斥量 + 命名管道转发 `--launcher` / `--quick-note` 参数。
- 自启动：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（保持现有行为）。
- 更新：保留 GitHub `latest.json` 与 minisign 公钥格式；下载 → 校验签名 → 备份 DB → NSIS `/S` 静默安装 → 失败自动回滚上一版本 exe。
- 安装：NSIS per-user，无 UAC；卸载时可选保留 `notes.db` 与附件。
- 日志：保留 `logs/app.log` 的环形 + 轮转策略，字段与现有 `logging.rs` 对齐，便于沿用排障手册。

### 5.7 架构门禁：分层与依赖约束

层次越清晰，重构越不容易烂尾。规则必须机器可检，而不是靠 review 记忆。

| crate | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|
| `app` | 装配根：初始化、窗口注册、命令路由 | 全部 | 业务逻辑、SQL、Win32 细节 |
| `hub-ui` | 视图、组件、主题、交互状态 | `hub-win`、`hub-core`、`hub-editor` | 直接 `use windows::*`、SQL、HTTP |
| `hub-editor` | RichEdit 文本岛与 Markdown 装饰 | `hub-core`、`hub-win` | `egui` 类型、业务状态 |
| `hub-win` | 窗口、DWM、托盘、热键、钩子、单实例、更新 | 无内部依赖 | `egui`、SQL、领域逻辑 |
| `hub-core` | 领域服务、SQLite、文件、解析 | 无内部依赖 | `egui`、`windows`、`tauri`、HTTP 客户端 |
| `hub-bridge` | scriptmgr worker 生命周期与协议 | `hub-core` | `egui`、`windows` UI 调用 |

硬规则：

1. **单向依赖，禁止环**：`app → hub-ui → hub-editor → hub-core`；`hub-win` 是被依赖方，不反向依赖任何业务 crate。
2. **平台能力只经 `hub-win` 暴露的 trait**：UI 层出现 `use windows::` 即违规。
3. **持久化只在 `hub-core::store`**：UI 不持有连接、不拼 SQL。
4. **网络只在 `hub-bridge`**：`hub-core` 不直接发 HTTP；worker 契约版本化 JSON。
5. **UI 与 core 只通过 DTO / 命令交互**，不共享可变全局状态。
6. **单文件 ≤ 800 行**；超出先拆模块，不靠注释分区。
7. **新增第三方依赖三问**：现有实现能否复用？owner 是谁？是否会让两侧同时拥有同一职责？答不清不加。

落地方式：

- `scripts/check-native-architecture.mjs`：解析 `native/crates/*/Cargo.toml` 的内部依赖边、扫描源码越界符号（如 `hub-core` 中的 `egui` / `windows::`）、检查 `native/` 下单文件行数；`native/` 尚未创建时打印 skip 并以 0 退出，保证现有 CI 不被阻塞。
- 接入 `scripts/run-smoke.ps1` 与 `.github/workflows/test.yml` 的 `architecture-gates` job；退出码 1 视为阻塞。
- 例外必须写 ADR（沿用 `docs/decisions/README.md` 的规则），不允许"先破后补"。

### 5.8 响应优先的实现清单（把成本前移到启动期）

热唤起要在 60 ms 内出首帧，就不能在按键那一刻做任何"创建型"工作。原则是：**启动期把所有固定成本付完，热键只做 `ShowWindow` + `Present`。**

| 预热项 | 做法 | 换来的 | 代价 |
|---|---|---|---|
| 窗口预创建 | 启动时创建 launcher 的 winit window，`visible=false`，尺寸/位置从设置恢复 | 省掉窗口创建 30–80 ms | ~2 MB |
| GL/D3D 上下文预热 | 启动时初始化渲染设备并绘制一帧到离屏纹理 | 省掉设备初始化 40–120 ms（集显最明显） | ~8–15 MB |
| 字体图集预栅格化 | 只预栅格化**首屏可见字符集**（Launcher 固定文案 + 最近项标题，去重后约 300–800 字），其余字符由 egui 按需增长；只保留跟随系统 DPI 的**单档** | 省掉首帧中文栅格化 20–60 ms；避免"先出框后出字" | 3–6 MB（150% DPI 下首屏字符集）。**不要预栅格化 3500 常用字**：150% 下字形面积 ×2.25，约 30 MB+，而首屏根本用不到 |
| 首帧纹理缓存 | 隐藏前保留最后渲染结果；显示时先 `blit` 缓存再增量重绘。**只缓存 Launcher 面板本身，不做全屏透明覆盖层** | 视觉上"瞬间出现"，首帧感知 ≈ 0 | 面板 440×860 逻辑 @150% ≈ **3.4 MB**（两缓冲 6.8 MB）；若做成全屏层（2560×1440 逻辑）则 ≈ **33 MB** 且触发额外合成路径。见 §5.1.1 |
| 最近项/收藏快照 | 启动时把 launcher 需要的数据加载进内存快照，变更时增量更新 | 首帧不查库、不等 worker | < 1 MB |
| SQLite 常开 | 连接常开 + WAL，启动期完成预热查询 | 省掉首次打开 30–100 ms（机械盘更明显） | ~2 MB |
| 脚本清单缓存 | `hub-core` 缓存脚本注册表，启动时异步刷新，**首帧不等 scriptmgr** | 把 Go worker 从首帧路径上摘除（见 Phase 5 评估） | < 1 MB |
| 输入法/排版前置 | 预创建 RichEdit 控件并设置默认格式，首次编辑只做内容加载 | 快速笔记打开即可打字 | ~3 MB |
| 事件驱动重绘 | 隐藏态与空闲态不调用 `request_repaint`；只有输入/动画/可见时才重绘 | 预热不等于持续耗电：空闲 CPU ≈ 0 | — |

关键结论：**§7.1 的 60 ms 不是靠运行时优化达成的，而是靠"按键时无可做事"达成的。** 如果实现后发现仍需 >60 ms，正确做法是继续前移成本，而不是把目标改成 120 ms。

#### 5.8.1 预热分级：常用预热，其余冷启动（2026-11-24 用户确认）

用户确认"60 ms 已经足够，最常用功能可以预热，其他功能冷启动"。这句话要落成一个**可判定的分档**，否则实施中会出现两种偏差：要么什么都预热（内存膨胀、冷启动变慢），要么什么都不预热（主门禁破线）。

**判定判据（唯一）：预热只覆盖"每天十次以上且首帧落在热路径"的能力。** 低于这个频率的一律冷启动，即使它"打开慢一点"。

| 档 | 判定 | 内容 | 目标 |
|---|---|---|---|
| **P0 启动预热（常驻）** | 每天数十次，首帧敏感 | Launcher 窗口 + 渲染设备 + 字体图集 + 首帧纹理缓存 + 最近项/收藏快照；快速笔记的 RichEdit 控件；SQLite 常开连接 | 热唤起 ≤ 60 ms |
| **P1 首开后常驻（进程内复用）** | 每天 1–2 次，但一次会话内反复用 | Manager 复用同一渲染设备与图集；笔记列表 FTS 连接保持；页面按访问懒加载，**首次打开后不销毁** | 同会话二次进入 ≤ 40 ms |
| **P2 冷启动（按需）** | 每周或更少 | 文件搜索、下载队列、语音/转写、relay、MCP、扩展、回收站深度扫描 | ≤ 400 ms 内出骨架，数据渐进填充；允许首屏是空态 |
| **不做预热** | — | 预加载笔记全文/缩略图、预创建 Manager 窗口、预热 T3 worker、开机预跑脚本发现 | — |

三档之间的关系是**成本分配**，不是"重要性排序"：P2 的功能一样重要，只是它的调用频率不足以支撑常驻成本。

同时明确**不做无限加码**：60 ms 落在"不可感知"区间，继续下探到 30–40 ms 需要更多预热，边际收益为零，但代价真实——**冷启动会变慢**，而冷启动正好是"灵感稍纵即逝"的另一个场景（开机后第一次按键）。用户把预算从内存挪给响应，是为了买"够快"，不是为了买"更快"。**若日后要下调目标，必须有实测证明 60 ms 可被感知，否则不加码。**

反面清单（明确不做，因为它们用响应换内存，方向反了）：

- 不做"关闭 Launcher 即销毁窗口"——省 2 MB，代价 30–80 ms，不划算。
- 不做"空闲时释放字体图集"——省 20 MB，代价是下次唤起重新栅格化，直接破坏主门禁。
- 不在热键回调里做同步 IO（读设置、开库、探活 worker）。

## 6. 实施计划

### Phase 0 度量与验证（1–2 周）

- 在本机（8 GB / 4 核 / 集显）采集三种姿态的内存/进程基线（静置 / Launcher / Manager+2 笔记，共约 5 分钟），写入本文件附录。**不找第二台机器、不做跨机对比**——内存不是可用性瓶颈，机器差异没有决策价值。
- **延迟才是 Phase 0 的重点**：S1 必须在本机拿到真实分布，而不是靠估算。
- 完成 S1/S2/S3/S4 四个 spike，产出结论与截图。
- 落地 `check-native-architecture.mjs` 骨架并接入 CI（`native/` 缺失时 skip）。
- 可选：`mstsc` 连本机回环，只验证"`lite` 是否被正确触发、触发后是否可操作"，不阻塞 G0。
- **G0 门禁**：四项 spike 达标 → 锁定栈版本，进入 Phase 1。其中 **S1 的热唤起 p95 ≤ 60 ms 是硬门槛**：它是唯一可能推翻整个栈选择的指标。本机就是标准环境，测不出来就是设计不成立，不允许"换台更好的机器再试"。

### Phase 0.5 先行止血（可选，2–3 天，低风险，可独立发布）

在 Phase 1 完成前，现版本仍有两套常驻 renderer。这一步不需要重写，只改窗口生命周期，能立刻拿回大部分静置占用：

- **`manager` 改为不预创建**（首次打开再建），这是主要收益来源。
- 快速笔记 / 待办卡片关闭时 `destroy`，不留在后台；已积累的窗口数量是占用随使用时长上涨的直接原因。
- 启动后释放未使用窗口的纹理与 DevTools。
- **修复开机自启动失效**（§2.4）：持久化偏好 + 启动对账 + 写入后校验 + 单实例回调尊重 `--autostart`。与窗口生命周期互不依赖，可一并发布。
- **`launcher` 保持预创建**（不做懒创建）。它是唯一有 60 ms 指标的面板，改成"热键才建"等于用主门禁换内存——已在 §5.8.1 的反面清单里明确禁止。这一步只改"不影响响应的窗口"。

价值：无需等待 Phase 1 就能验证"占用主要由隐藏的 manager 与未销毁的临时窗口造成"这一判断。**如果这一步的实测收益远低于预期，说明动因判断有误**，应在 Phase 0 就修正设计，而不是等到 Phase 2 才发现方向错了。

### Phase 1 常驻壳（2–3 周）

- `hub-win`：托盘、热键、鼠标钩子、单实例、自启动、日志、实色窗口（Mica 可选）。
- `hub-ui`：主题 token 骨架（color/typography/spacing/radius/elevation/motion）、Launcher、快速笔记壳、待办卡片。
- `lite` 模式探测与降级路径；**Manager 仍由现有 Tauri 进程按需启动**（共享 DB + 写锁）。
- **G1 门禁**：热唤起 p95 ≤ 60 ms（lite ≤ 120 ms）**阻塞发布**；常驻 ≤ 65 MB（lite ≤ 55 MB）为解释线，超线需说明；T0 功能 parity；连续 8 小时无句柄/内存增长；架构门禁常绿。

#### 过渡期约束（防止双栈固化）

双栈期最大的风险不是技术，而是"临时"变成"永久"。因此过渡不是开放式过渡，而是**责任逐格移交**，每格都有退出条件：

| 闸口 | 原生负责 | Tauri 负责 | 退出条件 |
|---|---|---|---|
| T-Gate 0（Phase 1 完成） | 托盘、热键、Launcher、快速笔记、待办卡片 | 仅 Manager | **Tauri 版必须停止创建 launcher / 快速笔记的 webview**，只保留一个按需的 Manager 实例 |
| T-Gate 1（Phase 2 完成） | 上述 + notes/inbox/todos/scripts/settings/trash | 仅 files/downloads/voice/relay/mcp/extensions 的旧页面 | 高频面板零 webview；低频面板走"打开旧版"入口 |
| T-Gate 2（Phase 3 完成） | 上述 + 完整编辑器 | 仅低频面板（可选保留） | 编辑器不再需要 WebView 退路 |
| T-Gate 3（Phase 4 完成） | 全部 | 无 | 删除 Tauri 依赖与 WebView2 profile |

硬性约束（违反即视为阻塞项）：

1. **任何时刻最多 1 个 WebView 进程**；Manager 关闭即销毁，不在托盘静置时存活。
2. **Tauri 版不得新增功能**；双栈期只修 P0 缺陷。新需求一律进原生实现。
3. **时间盒**：T-Gate 0 到 T-Gate 1 的窗口期不超过 8 周；超期则冻结低频面板功能，把资源全部投入迁移。
4. **每个 Phase 结束必须至少有面板从 Tauri 迁出**，不允许出现"只加原生、不减 Tauri"的相位。
5. 双栈期发布包同时包含两者，但安装器默认只注册原生 exe 为启动项；Tauri 版以内部入口存在，供回退使用。

### Phase 2 工作台（3–4 周）

- Manager 壳 + 笔记列表/搜索/收集箱/待办/脚本/设置/回收站（编辑器暂用只读预览 + 纯文本编辑）。
- 低频面板只做"状态 + 打开 worker 能力"的最小页。
- 主题系统覆盖全部页面；动效只用于状态变化，并服从"减少动画"。
- **G2 门禁**：日常路径 parity ≥ 90%；Manager 打开 ≤ 220 MB；页面切换 ≤ 80 ms；集显上列表滚动 ≥ 50 fps（lite / RDP ≥ 30 fps）。

### Phase 3 编辑器（3–4 周）

- RichEdit 文本岛：Markdown 装饰（标题/列表/引用/代码/链接）、待办 checkbox、图片粘贴与资源落盘、预览模式、自动保存、撤销/重做、快捷键。
- 输入法矩阵回归（微软拼音/搜狗/微信输入法）+ 一周 dogfood。
- **G3 门禁**：编辑 checklist 全绿；1 万字文档输入无卡顿；图片往返不丢；集显机输入无可感延迟。

### Phase 4 下线 Tauri（1–2 周）

- 删除 `easyflowhub-app`、`dist` 内嵌、`lib/tauri`、WebView2 依赖；更新器与安装器切换。
- 数据迁移演练：老库 → 新库 → 回滚老版本读新库。
- **G4 门禁**：新装 / 覆盖升级 / 回滚三条路径通过；卸载不残留 WebView profile；架构门禁与体积预算同时通过。

### Phase 5（v2 不做）Go worker 合并评估

**结论：v2 不合并 `scriptmgr-go`，保留为按需 worker。** 下面是依据，不是偏好。

先说清它现在是什么。`scriptmgr-go` 不是"脚本执行小工具"：81 个 Go 文件 / 20.3k 行（含 7.5k 行测试），已经包含六个独立子系统。

| 子系统 | 规模 | 性质 |
|---|---:|---|
| `internal/relay` | 687 行 + websocket | OpenAI 兼容流式代理，长连接 |
| `internal/mcp/{router,schema}` | 608 + 582 行 | MCP 协议实现与 schema 定义 |
| `internal/api/scriptfiles` | 672 行 | 脚本文件 CRUD 与校验 |
| `internal/hostconfig` | 656 行 | 宿主配置与路径约定 |
| `internal/executor`（含 async） | 423 + 相关 | 进程树、输出流、超时、Job Object |
| `internal/store` + `internal/notes/sync` | 512 + 365 行 | SQLite store 与笔记同步 |

依赖面很干净：`modernc.org/sqlite`（纯 Go，无 cgo）、`gorilla/websocket`、`fsnotify`、`uuid`、`humanize`、`isatty`，全部为 indirect。

#### 合并能换来什么

| 收益 | 量化 | 是否成立 |
|---|---|---|
| 常驻内存 | worker 采纳"空闲 60 s 退出"后本就不常驻；合并仅省 worker 活跃期的 12–20 MB | **接近 0**（v2 已用退出策略拿到） |
| 磁盘体积 | 省 `scriptmgr.exe` 16.6 MB，Rust 侧新增约 3–5 MB，净省 ~12 MB | 成立，但用户主诉不是磁盘 |
| 进程数 | 活跃期 -1 进程 | 成立，但只在脚本面板打开时 |
| **首帧延迟** | 本地回环 HTTP 0.2–2 ms/次；脚本列表 3 跳约 3–6 ms | **可由缓存消除，不必合并** |
| 数据一致性 | 消除"两个进程都写 SQLite"的结构性风险 | 部分成立，见下 |

关于响应：脚本清单**不该在首帧路径上**。`hub-core` 启动时缓存注册表、异步刷新，热键唤起只读内存快照（§5.8）。一旦这么做，合并对 §7.1 的贡献就是 0——这正是"不合并"最硬的理由：**为 3 ms 的本地 HTTP 重写 12.8k 行，投入产出不成比例。**

关于一致性：双写者是真实风险，但 Phase 2 把 notes/inbox/todos 收归 `hub-core` 唯一写者后，worker 只剩"脚本元数据 + 运行记录"两张表。风险从"核心数据竞争"降级为"边缘表竞争"，用命名互斥量 + WAL 即可覆盖，不需要合并。

#### 合并要付什么

- **重写 12.8k 行非测试 Go，并同步重写 7.5k 行测试**，预估 6–10 周全职，且**用户可见收益为零**。
- 三个硬骨头无法用"翻译"解决：`relay` 的 websocket 流式背压、`mcp` 的协议细节（schema 582 行是既成契约）、`executor` 的 Windows 进程树治理（Job Object、子进程回收、超时竞态）。
- goroutine → tokio 的并发模型换血，最容易在"输出流 + 超时 + 取消"三者交叉处引入新 bug，而这块当前已有 527 行输出测试在守着。
- 一旦合并，脚本能力的发布节奏就与主程序绑死，失去"worker 独立升级"这个现有的隔离优势。

#### 触发条件（满足任一，才重新评估）

| 判据 | 阈值 | 说明 |
|---|---|---|
| J1 关键路径 | Phase 2 实测脚本面板首帧 > 80 ms，且缓存方案无法消除 | 证明 HTTP 真进了热路径 |
| J2 一致性事故 | 出现 ≥1 次真实双写者数据冲突 | 从"理论风险"变"已发生" |
| J3 低端抖动 | lite 机上 worker 启停导致热键 p99 > 200 ms | 进程振荡影响主门禁 |
| J4 分发形态变化 | 需要单文件绿色版 / 免安装分发 | 这时合并的理由是"打包"，不是性能 |

替代方案（比合并便宜两个数量级，v2 采用）：worker **进程生命周期优化**——首次进入脚本面板时拉起、活跃后常驻 10 min（而非 60 s）、失败时降级为只读缓存并提示，不阻塞界面。


### 工期与体量估算（诚实版）

| 范围 | 现有代码量 | 目标 Rust 量级 | 全职 | 业余 |
|---|---|---:|---:|---:|
| 全量 parity（13 面板） | 23.3k 行 TS/TSX | 21–28k | 5–7 个月 | 9–15 个月 |
| **本设计 v2 收窄范围** | ~9k 行等价 | 10–14k + 4k 平台壳 | 3–4 个月 | 6–9 个月 |
| 仅 Phase 1 常驻壳 | — | 4–6k | 3 周 | 6–8 周 |

结论：**不做需求收窄的重写是 1 年工程，收窄后才是可交付的 3–4 个月工程。** 这也是本设计把 T3 推给 worker 的原因。

## 7. 验收指标

### 7.0 指标分级：响应是门禁，内存是约束下的次级目标（2026-11-24 用户确认）

用户明确选择**响应优先**："灵感稍纵即逝，启动必须要快"。这条选择改变了两件事：

1. **内存的角色是"响应约束下的次级目标"（2026-11-24 二次修正）**：既不是硬性阻塞项（8 GB 机器余量充足，内存不是可用性的瓶颈），也不是可以放任的预算——**在守住 §7.1 的前提下，能小就小**。判断标准很具体：不牺牲任何常用功能速度的省内存手段**必须做**；用响应换内存的手段**一律不做**。
2. **"热键 → 首帧"必须拆成三条**。之前合成一条 p95 掩盖了真实差异——冷唤起（进程未运行）和热唤起（进程已运行、窗口已预热）的体验差 5–10 倍，而日常路径 99% 是后者：

| 路径 | 发生频率 | 真实体验 |
|---|---|---|
| 热唤起（进程在、窗口已预创建） | 每天数十次 | 决定"是否愿意用" |
| 冷唤起（开机后第一次 / worker 已退出） | 每天 1–2 次 | 决定"第一次印象" |
| 窗口内切换（Launcher → 快速笔记） | 高频 | 决定"连续记笔记是否顺手" |

因此 §7.1 是**唯一阻塞发布的主门禁**，§7.2 是**次级目标 + 解释线**（超线要说明原因，但不阻塞功能），§7.3 是常规质量门禁。

### 7.1 主门禁：响应（唯一阻塞发布的指标）

| 指标 | standard | lite（软件渲染 / RDP） | 测量 |
|---|---|---|---|
| **热唤起 热键 → 首帧 p95** | **≤ 60 ms** | **≤ 120 ms** | `measure-native-latency.ps1`（原生壳，主动 `--bench`）；`measure-latency.ps1`（现 Tauri 版，仅作对照） |
| 热唤起 p99 | ≤ 100 ms | ≤ 200 ms | 同上，连续 200 次取分布 |
| 冷唤起（进程未启动）→ 首帧 p95 | ≤ 400 ms | ≤ 700 ms | `measure-latency.ps1 -ColdStart` |
| 冷启动 → 托盘就绪 | ≤ 300 ms | ≤ 500 ms | 同上 |
| 窗口内切换（Launcher → 快速笔记） | ≤ 40 ms | ≤ 80 ms | 同上，加自定义打点 |
| 键入到字符上屏（RichEdit） | ≤ 16 ms | ≤ 33 ms | `measure-native-editor.ps1`（原生文本岛，`--editor-bench`）；键击时间戳采样 |

注：`≤ 60 ms` 是"不可感知"的量级（100 ms 内人普遍认为是即时）。lite 放宽到 120 ms，但仍明显优于现状 WebView 的创建+JS 启动路径。**60 ms 是终点而不是起点**：达标即冻结预热范围，不再为个位数毫秒加码（理由见 §5.8.1）。

这个数字**包含"出现在光标处"的全部成本**：面板要定位到光标所在显示器、按该显示器缩放设置 ppp、夹紧到工作区，然后才呈现。因此显示器布局必须在启动期就缓存好，热键路径里不做枚举（见 §5.1.1 的三个坑）——否则多屏混合 DPI 环境下的 p95 会与单屏测量差出一个量级。

度量落地：主门禁必须有可执行的测量手段，否则它会退化成一句口号。新增 `scripts/measure-latency.ps1`：

```powershell
# 从日志统计热唤起分布（默认读 %APPDATA%\com.yukin.easyflowhub\logs\app.log）
powershell -NoProfile -File scripts\measure-latency.ps1
powershell -NoProfile -File scripts\measure-latency.ps1 -Lite -Json
# 冷唤起（要求应用未运行，不会杀进程）
powershell -NoProfile -File scripts\measure-latency.ps1 -ColdStart -ProcessPath dist\easyflowhub.exe -BudgetMs 400
```

脚本依赖一条**日志契约**（应用侧实现，Phase 1 的第一项任务）：

```text
2026-11-24 19:04:01.234 [INFO] [timing] hotkey_down
2026-11-24 19:04:01.290 [INFO] [timing] first_frame
```

在打点落地前脚本输出 SKIP 并返回 0，不会误报通过；已接入 `run-smoke.ps1`，步骤名为 `Tauri latency baseline (report)`，**带 `-NoFail`**。理由不是"想让它绿"：现版本实测 p95 101 ms，对 60 ms 目标**每次都会打印 `Verdict: FAIL`**，但它只是对照组，判决在原生壳上（见下方 S1 实测表）；让一个注定失败的步骤把整轮 smoke 长期染红，另外九个步骤就没人看了。退役前（P4）把它当回归护栏用：p95 越过 ~130 ms 才算真回归。**"SKIP" 不等于"达标"**——RC 发布前必须在**本机**拿到非空分布（本机是标准环境，不是边缘环境；不需要第二台机器）。

**Tauri 现状基线（2026-11-24 22:17 实测，n = 31 次真实热键唤起）**：

| 指标 | 现状 | 原生目标 | 差距 |
|---|---|---|---|
| p50 | 87 ms | — | — |
| **p95** | **101 ms** | **≤ 60 ms** | 需压掉 41 ms（−41%） |
| p99 | 130 ms | ≤ 100 ms | −30 ms |
| max | 130 ms | — | — |

口径说明：这是"热键回调 → `launcher-opened` 送达前端 → 连续两帧 → IPC 回程打点"，是**像素上屏的下界近似**，比真实呈现略乐观；即便如此仍比目标慢 41 ms。它的作用有两个：给原生壳一个可比的对照组，并证明门禁工具链（打点契约 → `measure-latency.ps1` → 分布）在原生壳出现之前就已经跑通。**G0 的判决仍用原生壳自己的首帧信号。**

**原生 S1 实测（2026-11-25，`native/`，n = 200 轮自动唤起，`scripts/measure-native-latency.ps1`）**：

| 指标 | 现状（Tauri） | 原生 S1 | 原生目标 | 结论 |
|---|---|---|---|---|
| p50 | 87 ms | **47.8 ms** | — | −45% |
| **p95** | 101 ms | **48.9 ms** | **≤ 60 ms** | **达标，余量 11.1 ms** |
| p99 | 130 ms | **49.3 ms** | ≤ 100 ms | 达标，余量 50.7 ms |
| max | 130 ms | 49.4 ms | — | — |

口径声明（与 C 批契约的差异必须一起读）：原生侧的 `shown` 是**热键消息 → `SetWindowPos` 返回**，此刻屏幕上是预热帧（隐藏态已画好的同一张面板），对应 §5.8 的"首帧感知 ≈ 0"；它不是"新内容绘制完成"。新内容的重绘另有打点，实测 p50 140 ms，因此面板内容最多滞后一次唤起——这一项**不计入门禁**，但记入风险（Phase 1 需要"显示即刷新"或数据快照版本号）。另外该数字跳过键盘驱动与 `RegisterHotKey` 的系统分发（任何实现都无法影响这一段），因此只用于栈选型对比，不能与其他产品的"按键到上屏"直接比较。细节见 [S1 文档 §9](./2026-11-25-native-shell-spike.md)。

**原生 S2 实测（2026-11-25，`native/`，150% 缩放，n = 200 @1k 字符 / n = 100 @10k 字符，`scripts/measure-native-editor.ps1`）**：

| 指标 | 原生目标 | 原生 S2（三次运行） | 结论 |
|---|---|---|---|
| **`type` p95（1k 字符文档）** | **≤ 16 ms** | **4.95 ms**（4.94 / 5.25 / 4.95） | **达标，余量 11 ms** |
| `type` p99 | ≤ 25 ms | **6.33 ms**（6.49 / 6.19 / 6.33） | 达标，余量 18.7 ms |
| `type` p50 | — | 2.9 ms（3.09 / 2.81 / 2.77） | — |
| `type` max | — | 6.8 ms | 未出现长尾卡顿 |
| **10k 文档 `type` p95** | **≤ 2 × 1k** | **5.09 ms**（5.30 / 5.09 / 4.69），比值 0.95–1.07 | **未退化**（曲线是平的，不是线性上涨） |
| `insert` / `repaint` 归因 | — | p50 1.7–2.0 ms / 1.1 ms | 成本在控件处理字符，不在重绘 |
| `compose`（合成，仅报告） | 不判定 | p50 4.9–7.5 ms，p95 7.6–9.6 ms | — |

口径声明（三条，缺一条上面的数字就不能用）：

1. **量的是"插入 + 显式重绘"，是上界而不是中位数**。RichEdit 在 `WM_CHAR` 内部同步绘制，所以 `UpdateWindow` 紧随其后耗时 0 µs（实测），"插入 vs 绘制"在自然路径上无法分开。因此门禁值 = `insert` + 一次强制的 `InvalidateRect` + `UpdateWindow` 全量重绘。两段有重叠，**这会高估真实成本**——对门禁来说是安全方向。
2. **合成不计入门禁**，与 S1 把"内容刷新"单列是同一个处理。`DwmFlush` 的返回值必然落在 `[paint, paint + 16.7]`，把它算进"键入到上屏"等于要求比一个刷新周期还快。**16 ms 这个数字没有改。**
3. **1.58 ms 那一版数据作废**。首次运行（60 轮、未取得焦点、桌面空闲）测出 p95 1.58 ms，但那个状态下 `EM_SCROLLCARET` 是空操作、DWM 也处于休眠（`DwmFlush` 返回 254 ms）。产品里文本岛拿到焦点后才会打字，所以只有带焦点的 4.95 ms 是可用的口径；被替换掉的口径连同原因记在 [S2 文档 §9](./2026-11-25-richedit-island-spike.md)，不留一个"看起来更快"的旧数字。

### 7.2 次级目标：常驻内存（响应达标前提下，能小就小）

**定位（2026-11-24 用户确认）**："在保障常用功能速度的情况下自然越小越好"。8 GB 机器上内存余量充足，内存不决定可用性，所以它**不是发布门禁**；但它决定"是否在逐版本滑坡"，所以要记录、要解释、要压。

先看清常驻内存由什么构成——这决定了"越小"到底还有多少空间（数值按本机环境校准：**3840×2160 @150%**，见 §2.1）：

| 构成 | 量级 | 性质 | 能否优化 |
|---|---|---|---|
| 渲染设备 + 上下文（GL/D3D） | 8–15 MB | **刚性**（预热 §7.1 的前提） | 不可削（削了就破主门禁） |
| 字体图集（**首屏字符集**预栅格化） | 3–6 MB（150% 下） | 半刚性 | 可压：只栅格化首屏可见字符、单档常驻（跨屏最多 2 档）、不用即不增长 |
| 首帧纹理缓存（1 份 440×860 面板） | 3.4 MB | 半刚性（取消后多 20–40 ms） | lite 下可取消 |
| 运行时 + egui + 状态数据 | 15–25 MB | 半刚性 | 可压：虚拟滚动、图片降采样、避免重复缓冲 |
| 预热数据快照（最近项/设置） | < 2 MB | 软性 | 已很小 |

**结构性下限约 30–50 MB**。注意这个下限随环境变化，**分辨率与缩放是主要变量**（逐档数值见 §5.1.1）：面积随缩放平方增长，4K@150% 下预栅格化 3500 常用字会吃掉 30 MB 以上、全屏首帧纹理要 33 MB——两者都能单独把常驻顶穿解释线。所以有两条硬设计约束（不是优化建议）：

1. **Launcher 是光标处的竖版面板（440×860 逻辑），不是全屏覆盖层，也不是工作台。** 缓冲只按面板尺寸分配：150% 下 3.4 MB，全屏层则是 33 MB，差 10 倍，且全屏透明层还会触发额外合成路径。
2. **图集只预栅格化首屏字符集**，其余按需增长。预栅格化"3500 常用字"看似稳妥，实际是把 30 MB 花在首屏用不到的字符上。

这就是为什么本指标用"解释线"而不是"逼近目标"：65 MB 在 4K@150% 下并不宽裕，而压到 30 MB 与 60 ms 在物理上不可兼得。

| 指标 | standard | lite | 性质 |
|---|---|---|---|
| 常驻 Private Bytes（托盘静置 5 min，**含预热的 Launcher**） | ≤ 65 MB | ≤ 55 MB | 解释线：超线需在 Phase 记录中说明原因 |
| Launcher 可见（含 1 个快速笔记） | ≤ 120 MB | ≤ 90 MB | 解释线 |
| Manager + 2 快速笔记 | ≤ 220 MB | ≤ 160 MB | 解释线 |
| 空闲 CPU（隐藏态、无重绘） | ≤ 0.2% | ≤ 0.1% | **阻塞项**（影响续航与风扇，且用户会直接感知） |
| 安装包体积 | ≤ 25 MB | 同 | 解释线 |

**必须做的免费优化（零响应代价，不做即视为回归）：**

1. 隐藏态/空闲态不重绘（`request_repaint` 只在输入、动画、可见时调用）。
2. 列表虚拟化；笔记正文按需加载，不预读全文。
3. 图片按显示尺寸降采样解码，不保留原图位图（磁盘留原件，内存留缩略）。
4. 关闭窗口时释放该窗口的 GPU 纹理与缓冲；字体图集与渲染设备**保留**（属 P0）。
5. 字体图集只保留单一 DPI 档，按实际字符集裁剪，不做多档并存。
6. worker（scriptmgr / T3）空闲退出，不滞留页面缓存。

**禁止的省内存手段（方向反了，会破 §7.1）：**

1. 关闭 Launcher 即销毁窗口。
2. 空闲时释放字体图集、下次唤起重新栅格化。
3. 取消预创建、退回"唤出时才建窗口"。
4. 为省几 MB 在热键回调里做同步 IO 或延迟加载设置。

**趋势记录**：每次 RC 用 `measure-footprint.ps1 -Json` 存一份快照（`docs/releases/` 下按版本归档）。若常驻连续两个版本上涨且找不到对应的功能增量，按回归处理——这条比单次数字更有用，因为"滑坡"只在趋势里看得见。

回退顺序（仅在超过解释线且需要压回时使用，从上到下，越靠下代价越大）：

1. 图集按字符集裁剪、去多档 → 省 5–10 MB，零延迟代价。
2. 取消首帧纹理缓存（lite 已有此策略）→ 省 4–8 MB，热唤起 +20–40 ms。
3. 取消最近项预加载 → 省 <2 MB，首帧多一次查库（有 SQLite 预热，约 +5–15 ms）。
4. 退回懒创建 → 省 2 MB，热唤起 +30–80 ms，**必须记 ADR 例外**。

### 7.3 常规质量门禁

| 指标 | standard | lite | 测量 |
|---|---|---|---|
| 首次打开到可操作（Manager） | ≤ 1.5 s | ≤ 3 s | 手动/脚本计时 |
| 列表滚动 | ≥ 50 fps | ≥ 30 fps | 内置帧时间采样 |
| 白屏 / 无法启动类故障 | 0 | 0 | 发布前 checklist |
| 架构门禁 | 常绿 | 常绿 | `check-native-architecture.mjs` |

## 8. 风险登记

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **热唤起 60 ms 在集显上不可达** | 中 | **高**（直接动摇主门禁） | 在本机集显做 S1 实测（这是标准环境，不是边缘环境）；依次前移成本（图集 → 纹理缓存 → 设备预热）；4K@150% 下控制首帧像素量（只呈现 Launcher 面板、不做全屏层、避免全屏透明合成）；仍不达标则走 ADR 例外把目标定为 100 ms，**不允许静默放宽** |
| 常驻内存逐版本上涨（温水煮青蛙） | 中 | 中 | §7.2 免费优化清单作为硬要求；每次 RC 用 `-Json` 归档快照，连续两版本上涨且无对应功能增量即按回归处理 |
| 中文 IME 在 RichEdit 岛中定位/组合异常 | 中 | 高 | S2 spike；必要时用 IMM32 手动定位候选窗；保留 WebView 编辑器作为临时退路 |
| 编辑器功能回退（图片、表格、粘贴） | 高 | 中 | parity checklist；图片走"编辑=文本 + 缩略条 / 预览=渲染"，与现有 UX 一致 |
| 主题/层次不达预期（简洁变成"简陋"） | 中 | 中 | 先定 token 与版式规范再写页面；每阶段做一次视觉 review；动效只做状态解释 |
| GL 初始化失败（老驱动 / 虚拟机）/ RDP 卡顿 | 中 | 高 | S1 覆盖 RDP 回环与软件渲染；`lite` 强制实色无动画；仍失败则评估 wgpu/DX12 或 GDI 兜底 |
| 架构门禁被绕过（临时例外堆积） | 中 | 中 | 门禁进 CI 阻塞；例外必须 ADR；每季度清理 baseline |
| 工期膨胀 | 高 | 高 | 严格 T0–T2 范围；T3 一律 worker；每阶段可发布 |
| 双栈写库冲突 | 中 | 高 | 命名互斥量单写者；升级前备份；schema 只加不改 |
| 自动更新/安装链路重做引入事故 | 中 | 高 | 复用 NSIS + minisign 格式；三条路径演练后再发版 |
| 无障碍能力弱于 Web | 高 | 低 | RichEdit 保留正文无障碍；壳层接受限制并记录 |
| egui 升级破坏渲染 | 中 | 中 | 锁版本 + 薄封装；升级作为独立 PR 验证 |

## 9. 决策状态

### 已确认（2026-11-24，第二轮约束 + 第三轮闭环）

1. **分阶段迁移 + 双栈共存**：接受；并明确要求"逐步过渡"，落为 Phase 1 的 T-Gate 0–3 责任移交表与 5 条硬性约束（含 8 周时间盒）。
2. **成熟方案优先**：egui + 系统 RichEdit 为主路径；G0 只锁定版本与细节，G0 失败才启用 C# WinUI 3 退路。
3. **目标环境**：最低 8 GB / 4 核 / 集显；4 GB 不再承诺可用。`lite` 改为应对软件渲染 / RDP 的降级档，**集显留在 standard**（原设计让集显进 lite 是错的，会导致主用户一直跑降级模式）。
4. **UI 简洁优先**：默认实色分层，不做毛玻璃/模糊/渐变/发光；主题系统负责美观。
5. **架构门禁**：crate 分层 + `check-native-architecture.mjs` + CI 阻塞；例外必须 ADR。
6. **响应优先（新增，优先级最高）**：主门禁为热唤起 热键→首帧 p95 ≤ 60 ms（lite ≤ 120 ms）；冷唤起 ≤ 400 ms。
   - 内存降为**响应约束下的次级目标**：在守住 60 ms 的前提下能小就小；65 MB（lite 55 MB）是解释线而非阻塞项，结构性下限约 30–50 MB（随分辨率/DPI 变化）。见 §7.2。
   - 为此明确接受三项代价：Launcher 启动即预创建、字体图集常驻、首帧纹理缓存。
   - 指标拆分为"热唤起 / 冷唤起 / 窗口内切换"三条，不再合成单一 p95。见 §7。
7. **T3 降级清单全部接受**：files / downloads / voice / relay / mcp / extensions 在 v2 只保留"状态 + 最小入口"，能力留在 worker。
8. **Mica 保留**：作为可选主题（默认关闭、Win11 且用户显式开启才启用），Win10 自动实色，`lite` 强制禁用。
9. **Phase 1 期间 Manager 仍由 Tauri 启动**：接受，但受 T-Gate 0 约束——Tauri 版须同步停止创建 launcher / 快速笔记的 webview，且最多 1 个 WebView 进程。
10. **预热范围定稿（2026-11-24）**：60 ms 已足够，不追加到 30–40 ms；只对"每天十次以上"的路径预热（P0 Launcher 链路 / P1 会话内复用），其余冷启动。分档与判据见 §5.8.1。这条同时约束了两端：不许为省内存砍掉 P0 预热（会破主门禁），也不许把 P2 能力拉进常驻（会拖慢冷启动、增加预热度过期类缺陷）。

### 已定论并保留复评判据

- **Go worker 合并：v2 不合并。** 依据见 Phase 5 评估：合并对 §7.1 的主门禁贡献接近 0（脚本清单走缓存，3–6 ms 的本地 HTTP 不在热路径），而成本是重写 12.8k 行 + 7.5k 行测试（6–10 周全职）、三个高风险子系统（relay 背压 / MCP 协议 / Windows 进程树）。触发 J1–J4 任一条件时重新评估，否则 Phase 4 之后不主动做。

### 无待确认项

设计层面的开放问题已清零，后续只由 G0–G4 的实测结果驱动调整。任何偏离本文件的取舍（例如把热唤起目标放宽到 120 ms）都必须走 ADR 例外，不允许在实施中口头变更。
