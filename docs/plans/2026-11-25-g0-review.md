## 1. 这份文档要回答什么

不是复述四个 spike 有多成功——那些数字在各自的 §9 里，这里只汇总。它要回答一个问题：**G0 该不该过。**

而"该不该过"不能靠"看起来都挺快"来答。按设计原文，G0 过 = 四项 spike 达标 → 锁定栈版本 → 进 Phase 1；任一项失败 = 回 ADR-0009 的退路（C# WinUI 3 或混合路线）。所以这份文档做三件事：

1. 逐条对照判据与实测，指出**哪条判据真的满足了、哪条没有证据**（§3）；
2. 把 14 个未测/未解项按"能否推翻栈选择"排开，而不是按文档顺序罗列（§4）；
3. 把设计文档没写清、必须由评审拍板的 4 件事单独拎出来，每件给出建议和"不这么选的后果"，再记下裁决结果（§5）。

## 2. 门槛原文（不改写）

§4.3 的通过标准：

| Spike | 通过标准 |
|---|---|
| S1 壳 | 热唤起 **p95 ≤ 60 ms**、p99 ≤ 100 ms；150% 单屏 + 模拟 100%/200% 各 200 次无泄漏；面板出现于光标所在屏且不被工作区裁切；预热后常驻 **≤ 65 MB（解释线，超线先记录原因再决定压缩顺序）**；RDP `lite` 可选 |
| S2 编辑器 | 微软拼音/搜狗/微信输入法**各 30 分钟无异常**；1 万字文档输入无可感延迟；Undo 栈正确 |
| S3 数据 | 读取全部笔记/待办/设置正确；写入后 Tauri 版本仍可读；无 schema 破坏 |
| S4 门禁 | 4 类故意违规全部报错，正常代码通过 |

§6 的判决规则原文：

> **G0 门禁**：四项 spike 达标 → 锁定栈版本，进入 Phase 1。其中 **S1 的热唤起 p95 ≤ 60 ms 是硬门槛**：它是唯一可能推翻整个栈选择的指标。本机就是标准环境，测不出来就是设计不成立，不允许"换台更好的机器再试"。
>
> 任何一项失败 → 回到 ADR-0009 的备选（C# WinUI 3，或"常驻原生 + 保留 WebView 工作台"的混合路线），**不硬推**。

## 4. 十四个未测 / 未解项（按"能否推翻栈选择"排序）

排序依据是：如果这项实测变坏，是要"换栈"（代价 = 重来），还是"多做活"（代价 = Phase 1 变长）。两种失败性质完全不同，不该混在一张表里。

### 4.1 不影响栈选择，但影响 Phase 1 工作量

## 5. 四个决定与裁决

### D1：常驻 130.1 MB（2.0× 解释线）怎么处理

设计原文只要求"**超线先记录原因再决定压缩顺序**"——记录已经做了（S1 §9 B9），"决定压缩顺序"在本次裁决里落定。这是 G0 唯一一个"判据没走完流程"而不是"判据没满足"的项。

#### 裁决前补的现网参照（2026-11-25 实测）

评审中给出的现场观察是："任务管理器里光 WebView2 就 200 MB，其中 180 MB 是 GPU 进程"。这条把问题从"我们超线"改写成"这条线的基准是谁定的"，于是把它实测了一遍，按**进程树归属**统计（不按映像名——`msedgewebview2.exe` 全机共用，按名字加会把别人的浏览器算到我们头上）：

| 分组 | 工作集 WS | 私有工作集（任务管理器「内存」列） | Commit（S1 自称的 Private Bytes） |
|---|---|---|---|
| WebView2 **GPU 进程** | 225.9 | **176.8** | 297.2 |
| WebView2 其余（host / renderer / 2×utility / crashpad） | 251.9 | 21.7 | 104.5 |
| `easyflowhub.exe` 本体 | 33.2 | 2.1 | 10.3 |
| `scriptmgr.exe` + `conhost` | 19.4 | 3.3 | 17.7 |
| **合计（9 进程）** | **530.4** | **203.9** | **429.6** |

口径对得上你的观察：WebView2 子树私有工作集 **198.5 MB**（≈ 你说的 200），其中 GPU 进程 **176.8 MB**（≈ 你说的 180）。差的那几 MB 是采样时刻不同，不是矛盾。

三列必须分开写，因为任务管理器「内存」列是私有工作集，而 Commit 通常是它的 2 倍。两个数都是真的，混着比就会得出"530 MB 的应用只占 200 MB"这种结论。

**这个数字能用来干什么、不能用来干什么：**

- 能：给出量级。130.1 MB 对 429.6 MB 是 **30%**，同一口径、同一台机器。
- 能：**GPU 进程一项的私有工作集（176.8 MB）就超过原生全进程的 Commit（130.1 MB）**。所以"130 MB 是退步"这个疑虑不成立。
- 不能：当受控对照。这是**单实例、已运行 645 分钟、有窗口**的一次采样（3 帧间隔 5 s 完全不变）；而 P0.5 记录的 262 MB 是"关掉 manager 窗口后的静置态"。状态不同，262 与 429.6 不可直接相减，本文不做这个减法。
- 读数族谱（防止被当成挑了一个最差的数）：**545.3 MB**（P0.5 前的托盘静置，设计 §2.2）、**262–283 MB**（P0.5 后关窗静置）、**429.6 MB**（本次，有窗口运行 645 min）。状态不同、数值不同，但都在原生 130.1 MB 的 **2–4 倍**量级，结论不依赖挑哪一个。
- 不能：证明原生侧在同口径下更省。原生只记了 Commit，**私有工作集没记**——这是 C1 要补的口径（三种都记），否则下次还会在同一处犯错。

复现：`powershell -NoProfile -File scripts/measure-process-tree.ps1 -ProcessName easyflowhub`（`-ProcessName app` 即原生壳；未运行时退出码 1，采样间漂移 > 2 MB 退出码 2）。

| 选项 | 内容 | 后果 |
|---|---|---|
| **A（建议）** | 接受 130 MB 作为已记录事实，Phase 1 把"字体子集化"列为第一项可量化优化，目标 ≤ 100 MB；**不改 65 这个数字** | 不改门禁、不写 ADR；G1 会再问一次（Phase 1 门禁同样写着 65 MB 解释线），届时用子集化后的数字回答 |
| B | 现在就做字体子集化再评 G0 | 追加 ~1 周，G0 推迟；但 130 MB 相对现网 429.6 MB 已是 30%（§5 D1 表现网实测），栈选择不会被这个数字推翻 |
| C | 把解释线改成 130 MB | **等于放宽门禁**，必须写 ADR 说明为什么 65 不可达、为什么 130 可接受。我不建议：现在的 130 是"还没做任何优化"的数字，拿它当新标准会让 Phase 1 失去优化动因 |

> **裁决（2026-11-25）：选 A。** 原话是"**不应该放宽门禁但接受现实，逐步优化**"，落成三条：
>
> 1. **65 MB 这个数字不动**，不写 ADR、不改门禁；
> 2. 130.1 MB 作为已记录事实进入 Phase 1，**字体子集化列为第一项可量化优化**（C1，目标 ≤ 100 MB）；
> 3. 目标值写进验收而不是写进意图——C1 要求"子集化前后对照 + 三种口径都记"。

理由（除上表现网参照外）：这条线在设计里是"解释线"而非硬门槛，硬门槛 60 ms 已过且余量 18%；130 MB 里那 37.7 MB 是**可单独量化、单独验收**的字体开销，价值在于"能被一个任务消掉"，而 G0 阻塞不会让它变小；现在改成 130 MB 等于把"还没做任何优化"的数字定成标准，Phase 1 就失去优化动因——这正是"放宽门禁"的典型形态。

**同时必须记下的风险**：65 MB 有可能**根本达不到**。92 MB 基线是 GL 驱动 + winit + egui，字体子集化后大概落在 92–100 MB。若 C1 到 100 MB 就压不动，说明 65 在设计时未经过实测校准——**届时由 G1 判断是否改线，且必须写 ADR**，不能在 Phase 1 里悄悄挪。现在不改，不等于永远不改；区别是改的时候手里有数字。

### D2：S2 的"三种输入法各 30 分钟"要不要当作 G0 的阻塞项

这是四项 spike 里**唯一一条没有证据的判据**。严格按"四项达标才过"，现在不该过。

| 选项 | 内容 | 后果 |
|---|---|---|
| **A（建议）** | 不阻塞 G0，但设成 Phase 1 的**硬性出口条件**（第一周内完成，写入 T-Gate 0 的退出条件） | G0 可以启动 Phase 1 的壳工作（与编辑器无关的部分），IME 验收在最坏情况下的代价仍然可控 |
| B | 现在补测（需要你或我操作机器，约 90 分钟） | G0 严格闭合，Phase 1 起点干净；代价是今天要有人坐在机器前 |
| C | 记为"接受风险"，不定期限 | 不建议：无期限的条件等于没有条件 |

> **裁决（2026-11-25）：选 A** —— 不阻塞 G0，但作为 **Phase 1 第一周硬性出口条件**（C2），逾期未做则 Phase 1 的壳工作暂停补测。

理由：S2 已经证明的恰恰是"最可能坏的那部分"——IME 消息链路不被吞（`ImmGetContext` 非 NULL、`WM_IME_*` 全部走 `DefSubclassProc`、子类化只吃 `WM_KEYDOWN` 里的 ESC/TAB）。剩下的是系统组件（RichEdit + 输入法本身）的成熟度，坏的概率低，但**低不等于零**，所以必须有期限——无期限的条件等于没有条件。

### D3：`journal_mode=delete` 保持不动，还是切 WAL

S3 全程只读不写 schema，`journal_mode` 未改。切 WAL 会把文件头 write version 改成 2、留下 `-wal`/`-shm`，影响备份脚本、文件复制、同步工具——这是**产品级决定**，不该由 spike 替用户定。

> **裁决（2026-11-25）：保持 `delete`，不动。** ADR **现在不写**——写了也只能写"暂不切换"，是空文档；改为**登记触发条件**：出现"双写者（原生与 Tauri 同时写同一库）"或"同步/备份/云盘工具并发访问"任一情形时，先写 ADR 再动 `journal_mode`。
>
> 理由：并发实测已证明 `IMMEDIATE` + `busy_timeout` 能吸收 400 ms 短锁、明确拒绝 7 s 长锁且不留半行；WAL 的收益（读写不互斥）在单写者阶段用不上，而代价（文件头 write version=2、`-wal`/`-shm` 伴生文件破坏现有备份与复制脚本）是立刻要付的。触发条件已写进 `docs/roadmap.md` 的 Native Runtime Track「待办」，避免这条只以"某人记得"的形式存在。

### D4：是否锁定栈版本并进入 Phase 1

| 选项 | 内容 |
|---|---|
| **A（建议）** | G0 **有条件通过**：锁定 egui/eframe **0.31**、RichEdit（系统组件不锁版本）、`rusqlite 0.32 bundled`，进入 Phase 1 |
| B | 不通过，回 ADR-0009 退路——目前没有任何证据支持这一条（见 §6） |

> **裁决（2026-11-25）：选 A，有条件通过。** 锁定 egui/eframe **0.31**、`rusqlite 0.32 bundled`、RichEdit（系统组件，不锁版本）；进入 Phase 1，退出条件见 §7。

**关于"锁版本"的严格含义**：egui/eframe 钉住 0.31 不是审美选择——**所有归档的延迟样本**（S1 的三档缩放、S2 的三次运行）都是在这两个版本上采的，升级即作废全部基线。Phase 1 若要升版本，必须先重采基线，否则 G1 的 60 ms 判决失去可比性。

## 6. 如果现在否决，代价是什么

否决的合理理由只有一条：**"未测项还太多，不该往下走"**。

但这个理由在这里不成立，因为 §4 里那 14 项**不会因为继续做 spike 而变少**：

- 多屏混合 DPI 需要**第二块显示器**，不是多做一轮实验；
- 三种输入法需要**人**，而且需要人会打中文；
- Win10 双系统需要**另一台机器**；
- 22 389 个附件的批量读取需要把整个 `assets/` 复制进工作区，只为证明"文件还在"；
- 随机并发压力属于 Phase 2 的双写者课题。

也就是说，继续停在 Phase 0 只会让 Gate 空转，不会让证据变多。而 ADR-0009 的退路（C# WinUI 3 / 混合路线）需要的触发证据——"硬门槛不过"——**不存在**：硬门槛 48.9 ms 对 60 ms，余量 18%。
