# ADR-0003 产品方向与动作优先

- status: accepted
- date: 2026-10-16

## 背景

EasyFlowHub 的产品画像经历了从 `AllScripts` 脚本管理，到包含快速笔记、待办、脚本执行、桌面窗口和 AI 集成的桌面效率工具的变化。当前代码已经拥有多个可用能力，但用户主路径仍主要表现为 Manager 中彼此独立的功能面板：

- quick note 负责快速捕获，notes manager 负责整理；
- todo 负责从 Markdown 聚合行动项；
- scriptmgr 负责脚本发现、参数校验、执行和历史；
- relay、MCP、extensions 提供面向 AI 工作流的受控集成。

这种结构能承载功能，却没有回答用户每天最常见的问题：在当前窗口、选中文本、剪贴板或文件上下文中，下一步该做什么，以及如何用最少的切换完成它。

产品方向参考 Quicker 一类桌面效率工具的动作模型，但不以复制其界面或完整扩展生态为目标。EasyFlowHub 需要优先服务个人效率用户，同时保留开发者和 AI 工作流用户的高级能力；Windows-first 的全局快捷键、托盘、多窗口和悬浮窗口是主要体验边界。

## 决策

### 1. 用户与平台优先级

1. 首要用户是个人效率用户，目标是降低记录、整理和执行任务的切换成本。
2. 开发者、本仓库维护者和 AI 工作流用户是高级集成用户，relay、MCP、host routing 和 extensions 面向这些用户提供受控增强。
3. 产品继续采用 Windows-first 策略，优先保证全局快捷键、托盘、多窗口、悬浮窗口、桌面固定和打包产物行为。

### 2. Hub + Launcher + Manager 三层产品结构

1. **Hub** 是共享的产品中枢，承载应用状态、动作库、数据和统一反馈。Hub 是产品概念，不要求立即新增一个代码模块。
2. **Launcher** 是面向日常使用的低打扰入口，通过全局唤起、搜索、最近使用和收藏动作，把当前上下文连接到下一步操作。
3. **Manager** 是面向整理、配置、审计和恢复的工作台，继续承载笔记、待办、脚本、设置以及受控 AI 集成。
4. Manager 不再被视为所有日常操作的唯一入口；Launcher 与 Manager 应形成互补关系。

### 3. Capture + Act + Flow 能力分层

1. **Capture** 负责快速笔记、剪贴板、选中文本和文件捕获，并把内容放入可继续整理的 Inbox / 笔记。
2. **Act** 负责执行脚本、应用、URL、文本和文件动作，并把结果写回剪贴板、文件、笔记或通知。
3. **Flow** 负责把多个动作组合成可复用流程，后续逐步加入参数传递、条件、重试、取消和输出路由。
4. v1.0.0 主要完成 Capture 与 Act 的稳定基础；Flow 保持为后续演进方向，不作为当前发布阻塞项。

### 4. 版本演进策略

1. 当前 `0.1.1` 包线的下一轮用户体验版本是 `v0.2.0`，优先验证个人效率 Hub：截屏、翻译、Inbox 捕获、文件检索、下载、录音和录音后转写。
2. v1.0.0 不重写现有应用，不因产品方向调整而推迟 quick note、notes manager、todo、scripts、manager/settings 和 Windows 行为的稳定发布；相关文档继续作为既有发布治理基线。
3. v1.1.0 的第一长期平台目标是 Action Launcher：统一动作搜索、全局唤起、最近使用、收藏、参数输入和执行结果反馈，并在 v0.2.0 的上下文契约基础上继续演进。
4. v1.1.0 不承诺一次完成复杂 Flow 编辑器、社区动作市场、云同步、多端协作或任意代码插件执行。

### 5. Owner 与边界

1. `easyflowhub-app/src/modules` 继续拥有 Manager builtin module 的注册和启停，不承担通用 action registry。
2. Action registry 的长期 owner、触发器、输入输出、权限和执行记录必须在实现前单独确定，不得把 Launcher 逻辑散落到现有面板。
3. `scriptmgr-go/internal` 继续拥有脚本发现、参数校验、执行和任务记录；Launcher 通过稳定接口消费这些能力，不复制脚本业务逻辑。
4. relay、MCP、host routing 和 extensions 继续作为受控高级能力接入，不能成为个人效率用户的首屏主叙事，也不能反向阻塞 v1.0.0 核心发布。

## 影响

- 用户理解产品的方式从“笔记、待办、脚本几个面板”转为“在当前上下文中快速完成动作，并在需要时进入 Manager 整理”。
- 现有 quick note、todo、scriptmgr、托盘和悬浮窗口能力获得统一的产品演进方向，可以逐步包装为 Capture 或 Act 能力。
- v1.0.0 的实现范围保持稳定，避免因品牌和定位变化触发大规模重写。
- v1.1.0 需要新增 action registry / contract，并处理 Launcher 与 Manager module registry 的边界；这是新的设计工作，不能由现有页面结构自然推导出来。
- Flow、扩展市场和更强 AI 编排会被延后，换取先验证 Launcher 是否真正减少切换和重复输入。

## 备选方案

### 方案 A：继续以 Manager 面板为唯一产品主入口

- 不采纳原因：保持了当前实现形态，但用户仍需先进入管理页面再寻找动作，无法充分发挥全局快捷键、托盘和桌面上下文的效率优势。

### 方案 B：把产品收缩为纯脚本管理器

- 不采纳原因：与当前已形成的笔记、待办、窗口和 AI 集成能力不一致，也无法覆盖个人学习和工作中的捕获、整理需求。

### 方案 C：立即重写为完整 Quicker / 插件市场平台

- 不采纳原因：会把动作模型、流程编排、扩展执行、权限、市场和同步同时引入，无法满足 v1.0.0 的稳定发布目标。

## 验证

- `docs/PROJECT_PROFILE.md` 已记录个人效率用户优先、Windows-first、Hub + Launcher + Manager 以及 Capture / Act / Flow 分层。
- `docs/roadmap.md` 已将 Action Launcher 设为 v1.1.0 首要产品目标，并明确 v1.0.0 不重写。
- 当前文档链接和版本表述应在每个 release checkpoint 继续与 PRD、README 和实现状态同步。

## 后续工作

1. v1.0.0 发布后，盘点现有脚本、笔记、待办、窗口和小组件可复用的动作入口。
2. 新增 Action Launcher 设计文档，明确 action registry / contract：动作身份、触发器、输入、输出、权限、执行状态和历史。
3. 以脚本收藏/最近动作和最小全局入口作为第一批验证，暂缓复杂 Flow 编辑器与社区市场。
4. 如果 action registry 改变现有模块 owner 或跨层协议，再新增或更新对应 ADR。
