# ADR-0009 Windows 原生运行时与 UI 栈

- status: accepted
- date: 2026-11-24
- scope: v1.2+（Native Runtime track；栈细节由 G0 锁定，2026-11-24 用户确认方向）
- related plan: [../plans/active/2026-11-24-native-runtime-redesign.md](../plans/active/2026-11-24-native-runtime-redesign.md)
- supersedes: 无（与 ADR-0003 的产品方向兼容）
- amends: ADR-0004 §2（玻璃材质的实现手段；视觉方向不变）

## 背景

EasyFlowHub 当前是 `Tauri 2 + React 19 + Go sidecar`。产品事实是 **Windows-only**：快捷键、托盘、悬浮窗、桌面固定、录音、下载队列都只在 Windows 上验证过，跨平台能力从未被使用。

2026-11-24 实测（`scripts/measure-footprint.ps1`）：**托盘静置（manager / launcher 均 `visible: false`、无人操作）Private 545.3 MB / Working Set 846.1 MB / 10 进程**——WebView2 占 7 个进程、合计约 514 MB，最大单进程 352.9 MB；启动后 30 s 与 130 s 两次采样为 564 → 546 MB，确认是稳态而非启动峰值。**该数字是本 ADR 最直接的动因证据：没有任何可见窗口、没人操作，常驻仍是 65 MB 解释线的 8.4 倍。** 磁盘侧：安装目录 39.4 MB、`easyflowhub.exe` 22.8 MB、`scriptmgr.exe` 16.6 MB、WebView2 用户数据 55.5 MB（每次启动约增长 2 MB）；系统 WebView2 Runtime **2029.3 MB**（v158，共享，不计入安装体积；10 月同一脚本记录为 878.7 MB / v157，一个月翻倍）。内存随窗口数线性增长的结构性原因：`manager` / `launcher` 以 `visible: false` 创建，每个快速笔记 / 待办卡片再新建一个 `WebviewWindow`，每个窗口一套 Chromium renderer。

用户已确认四条约束：

1. **分阶段**推进，不一次性切换。
2. **优先成熟方案**，不赌实验性框架。
3. **尽量降低占用**，并适配集显与远程桌面（最低 8 GB；4 GB 不承诺）。
4. UI **简洁明了优先**，避免复杂特效；但保留主题系统，让界面美观、动效得体。

产品语义补充（用户澄清，2026-11-24）：**Launcher 是"跟随光标的动作面板"**（形态参考 Quicker 快速面板——竖版多列动作网格，出现在光标处，选中即执行/消失），**工作台（Manager）是另一个窗口、另一种入口**。两者不合并，也不共用窗口。这个语义直接决定了首帧缓冲只有面板大小（440×860 逻辑，150% 下 3.4 MB），而不是屏幕大小（33 MB）。

此外要求**加强架构门禁与依赖约束**，让层次清晰、易于维护。

## 决策

### 1. 目标运行时：单进程原生 Rust，不再用 WebView 承载常规 UI

一个 `easyflowhub.exe` 承载窗口、托盘、热键、数据库与常规页面。不保留"隐藏窗口里的 webview"，不以 Electron / WebView2 作为 UI 运行时。

### 2. UI 栈：`egui` 外壳 + 系统 `RichEdit` 文本岛（成熟度优先）

- **外壳与常规页面用 egui**：单一渲染栈、无 JS 运行时、与现有 10.8k 行 Rust 壳同语言；即时模式对多窗口 / 悬浮 / 自绘最直接。
- **笔记正文用 Win32 `RICHEDIT50W`**：IME、候选窗定位、撤销、选区、右键菜单、高对比度、无障碍全部由系统提供。RichEdit 是 Windows 上最成熟的文本控件，避免自研文本引擎这一最大风险。
- **成熟度判定标准**：组件必须满足"有长期维护 + 有生产使用 + 有可替换退路"。RichEdit 满足；egui 满足（稳定发布节奏、工具类桌面应用广泛使用）；不引入 DSL 框架（Slint）与自研 UI 框架。
- **退路**：G0 验证失败则改用 C# + WinUI 3（Windows 原生控件最成熟），或"常驻原生 + 保留 WebView 工作台"的混合路线；不硬推。

### 3. 目标环境：8 GB 起，集显是常态（2026-11-24 修正）

- 最低支持配置：Windows 10 22H2 / 4 核 / **8 GB RAM** / 集显 / 1366×768；可用性不低于"打开 3 秒内可操作"。
- **4 GB 不再作为目标**：允许启动，但不承诺性能、不进 CI、不占预算。用户确认 4 GB 办公机已基本淘汰，"运行 Win10 都勉强"。
- **集显走 standard，不进 lite。** lite 只用于 GL 初始化失败（软件渲染）或远程桌面会话，目的是应对渲染能力缺失与带宽受限，而非内存不足。原设计把集显列为 lite 条件，会让主用户长期跑降级模式——这是错的，已修正。
- 渲染后端以 OpenGL（glow）为主；lite mode 关闭动画、阴影、透明与背景模糊，只保留实色分层。
- 字体图集在启动期**只预栅格化首屏可见字符集**（Launcher 文案 + 最近项标题，约 300–800 字），其余字符按需增长；lite mode 再收窄到"启动界面上必然出现的字符"。不内嵌大体积字体，不做多 DPI 档并存。**不采用"空闲时释放图集"**，因为重新栅格化会直接破坏响应门禁（见第 8 条）。
- **注意分辨率与 DPI 的乘数效应**：本机为 3840×2160 @150%，字形面积 ×2.25、纹理按物理像素计。设计估算必须按这个环境校准，不能用 1366×768 的数值外推。
- 内存是**响应约束下的次级目标**（见 plan 第 7.2 节）：在守住热唤起 60 ms 的前提下"能小就小"；65 MB（lite 55 MB）是**解释线**而非阻塞项，8 GB 机器上内存不决定可用性。零响应代价的省内存手段必须做，用响应换内存的手段一律不做。
- **度量范围只在本机**：不设第二台低配机、不做跨机对比。需要精确的是延迟，不是内存——机器差异对"该不该换架构"没有决策价值。

### 4. UI 方向：简洁优先 + 主题系统 + 克制的动效

- 默认是**实色分层**：背景、表面、边框、文字四级层次，细边框 + 极轻阴影；不做毛玻璃、模糊、渐变、发光。
- Mica / Acrylic 仅作为"能力允许时的可选主题"，不是默认；Win10 自动降级为实色。
- 主题系统统一管理 `color / typography / spacing / radius / elevation / motion` 六类 token；所有页面只消费 token，不写魔法值。
- 动效只用于状态变化（面板进出、列表项增删、焦点迁移），统一时长与缓动；**尊重系统"减少动画"设置**。
- 视觉验收标准从"像网页"改为"层次清楚、信息密度合适、集显机不卡"。

### 5. 架构门禁：crate 分层 + 机器可检的依赖约束

- 依赖方向固定：`app → hub-ui → hub-core`，`hub-win` 只被 `app` / `hub-ui` / `hub-editor` 使用，`hub-core` 不依赖 UI 与 Win32。
- 新增 `scripts/check-native-architecture.mjs`：解析 `native/crates/*/Cargo.toml` 的依赖边、扫描源码中的越界符号（如 `hub-core` 出现 `egui` / `windows::`）、限制单文件规模；接入 `run-smoke.ps1` 与 CI。
- 新增第三方依赖必须说明用途与 owner，并更新 `ARCHITECTURE_GUARDRAILS.md` 的 native 段。

### 6. 数据契约不变，迁移期单写者

- 继续使用现有 `notes.db`、附件目录与设置表；schema 迁移只加列不改语义。
- 双栈共存期同一时刻只允许一个写者（命名互斥量 + `schema_version` 校验）。

### 7. 迁移采用绞杀者模式，Tauri 版本保留到功能对齐

先常驻壳（收益最大、风险最小），再工作台，最后编辑器；每阶段有可回退点与门禁。

迁移期以"责任逐格移交"约束，**不允许只增原生、不减 Tauri**：Tauri 版在 Phase 1 就必须停止创建 launcher / 快速笔记的 webview，全程最多 1 个 WebView 进程，且 T-Gate 0→1 窗口期不超过 8 周。

### 8. 响应优先于内存（2026-11-24 追加，优先于第 3 条的"尽量降低占用"）

用户判定："灵感稍纵即逝，启动必须要快"，明确选择**以常驻内存换响应速度**。这使第 3 条的"尽量降低占用"退为约束条件，而不是优化目标。

- **主门禁是响应，不是内存。** 热唤起（进程在、窗口已预热）热键→首帧 p95 ≤ 60 ms（lite ≤ 120 ms）；冷唤起 ≤ 400 ms。只有这一组指标阻塞发布。
- 内存降为**次级目标**：在守住上面这组响应的前提下能小就小。常驻 ≤ 65 MB（lite ≤ 55 MB）是**解释线**而非阻塞项——超线要说明原因，但不阻塞功能；同时也不许为了压数字去牺牲热唤起（结构性下限约 30–50 MB，低于它一定砍掉了预热）。
- **两条与分辨率/DPI 相关的硬约束**：Launcher 是**光标处的竖版动作面板**（440×860 逻辑像素，Quicker 式，不是全屏遮罩、不是工作台）而非全屏覆盖层；字体图集只预栅格化首屏字符集（约 300–800 字），不预栅格化 3500 常用字。在 4K@150% 下违反任一条即可单独顶穿解释线（全屏首帧纹理 ≈33 MB 对面板 3.4 MB、3500 字图集 ≈30 MB+）。
- **缓冲只按面板尺寸分配，不按屏幕尺寸分配**：这是 3.4 MB 与 33 MB 的差别。图集与图标缓存按缩放分键，跨屏最多保留 2 档（当前档 + 上一档），DPI 切换时新旧档交接以消除"文字空白一帧"。
- **60 ms 包含光标定位成本**：显示器布局（工作区 + 缩放）在启动期缓存、在 `WM_DISPLAYCHANGE`/`WM_SETTINGCHANGE` 时失效重建；热键路径只做 `GetCursorPos` + 查缓存 + `SetWindowPos`，**不枚举显示器**，且 `pixels_per_point` 必须在 `show` 之前设好，否则会先闪一帧错误缩放。详见 plan §5.1.1。
- 判断标准写死：**零响应代价的省内存手段必须做**（隐藏态不重绘、列表虚拟化、图片降采样、关窗释放纹理、图集单档裁剪、worker 空闲退出）；**用响应换内存的手段一律不做**（关闭即销毁 Launcher、空闲释放图集、取消预创建）。
- **指标必须拆三条**：热唤起 / 冷唤起 / 窗口内切换。合成单一 p95 会掩盖 5–10 倍的体验差异。
- 实现原则是"启动期付完固定成本，热键时无可做事"：预创建 Launcher、预初始化渲染设备、预栅格化字体图集、缓存首帧纹理、脚本清单读缓存（不让 worker 进首帧路径）。
- 明确禁止的反向优化：关闭即销毁 Launcher、空闲时释放字体图集、在热键回调内做同步 IO。
- 若实测无法达到 60 ms，正确响应是继续前移成本；放宽目标必须走 ADR 例外。
- **预热范围有边界（2026-11-24 定稿）**：用户确认 60 ms 已足够，**不追求 30–40 ms**。预热只覆盖"每天十次以上且首帧在热路径"的能力——P0（Launcher 窗口 / 渲染设备 / 字体图集 / 首帧纹理 / 最近项快照 / 快速笔记控件 / SQLite 常开）与 P1（会话内复用 Manager 渲染设备与 FTS 连接）；P2 低频能力（文件搜索、下载、语音、relay、MCP、扩展、回收站深扫）一律冷启动，允许首屏空态渐进填充。理由是继续下探的边际收益为零，而更多预热会拖慢冷启动——开机后第一次按键同样是"灵感"场景。分档与判据见 plan §5.8.1。

### 9. 其余三项定论（2026-11-24）

- **T3 降级清单全部接受**：files / downloads / voice / relay / mcp / extensions 在 v2 只保留"状态 + 最小入口"，能力留在 worker。
- **Mica 保留为可选主题**：默认关闭，Win11 且用户显式开启才启用，Win10 自动实色，lite 强制禁用。
- **v2 不合并 Go worker**：合并对响应门禁的贡献接近 0（脚本清单走缓存，3–6 ms 的本地 HTTP 不在热路径），而成本是重写 12.8k 行 + 7.5k 行测试，并触碰 relay 背压、MCP 协议、Windows 进程树三个高风险区；仅在 plan 中 J1–J4 判据触发时复核。替代方案是 worker 生命周期优化（活跃后常驻 10 min、失败降级只读缓存）。

## 备选方案与不选理由

| 方案 | 成熟度 | 结论 | 原因 |
|---|---|---|---|
| 继续优化 Tauri（单窗口复用、懒创建、关 GPU） | 高 | 不采纳为主路径 | 可把基线从"两套 webview"降到"一套"，但 Chromium 多进程基线仍在，集显机无解 |
| **Rust egui + RichEdit 文本岛** | 中高 | **采纳** | 单进程、低占用、文本交给系统；UI 简洁化后其"工具风"劣势不再重要 |
| Rust + Slint | 中 | 备选 | 声明式更接近现视觉，但复杂文本编辑与 IME 证据少，需新学 DSL |
| C# + WinUI 3 / WPF | 高 | 备选（G0 失败时） | 原生控件与 Mica 最省事，但换语言栈、self-contained 体积大、集显机内存偏高 |
| Go + Fyne / Walk | 中低 | 排除 | 中文 IME、文本编辑与自绘视觉是硬伤，与"低占用 + 简洁"目标不符 |
| 纯 Win32/D2D 全自绘 | 高 | 排除为起点 | 控制力最强但 UI 开发速度最慢，只作为性能兜底 |

## 影响

正面：

- 常驻内存从"每窗口一个 renderer"变为"单进程 + 预创建窗口"，解释线 ≤ 65 MB（lite ≤ 55 MB）；相比现状的数百 MB 是数量级下降，且在此之上仍坚持"零响应代价的优化全部要做"。
- 热唤起不再经过 WebView 创建与 JS 启动，目标 p95 ≤ 60 ms；这是本 ADR 的第一优先级指标。
- 白屏类故障（profile 损坏、内嵌旧资源）从根上消失；发布链路只剩 `cargo build` + NSIS。
- UI 去特效后，集显机与远程桌面的可用性显著提升；主题系统仍保留美观与动效空间。

负面 / 代价：

- UI 需要重写：非测试前端 23.3k 行；v2 收窄范围约 9k 行等价物，仍是全职 3–4 个月量级。
- **为响应主动多付约 30 MB 常驻**（预创建窗口 + 字体图集 + 首帧纹理缓存）。这是第 8 条的代价，接受它。
- 失去 Web 生态：Markdown 编辑器、Tailwind、React 组件库、现有 413 项前端测试不能直接复用。
- egui 的字体渲染、控件密度与网页不同，需要重新校准（但已不再追求重度视觉还原）。
- 迁移期双栈维护，文档与验证成本上升；须靠 T-Gate 与时间盒约束，否则容易固化。

## 验收与退出条件

- Phase 0 的 G0：四项 spike 通过（壳 / 编辑器 / 数据 / 门禁），**S1 必须实测热唤起 p95 ≤ 60 ms**（lite ≤ 120 ms）——这是最可能推翻本 ADR 的一项；若 60 ms 在集显机不可达，要么调整预热手段，要么把目标写入例外，不得默默放宽。
- 响应必须可测量：`scripts/measure-latency.ps1` 读日志中的 `[timing] hotkey_down` / `[timing] first_frame` 配对给出分布；打点未落地时输出 SKIP 并返回 0，**SKIP 不等于达标**，RC 前必须拿到非空分布。
- 内存以**趋势 + 解释线**判定：常驻 ≤ 65 MB（lite ≤ 55 MB）超线需说明原因；每次 RC 用 `measure-footprint.ps1 -Json` 归档，连续两版本上涨且无对应功能增量即按回归处理。压缩顺序：图集裁剪 → 取消纹理缓存 → 取消最近项预加载 → 懒创建（最后一项需 ADR 例外）。
- `check-native-architecture.mjs` 必须在 CI 中常绿；越界依赖一律视为阻塞项。
- 迁移期 T-Gate 0–3 必须逐格推进，不得出现"只加原生、不减 Tauri"的相位。
- G0 通过后本 ADR 保持 `accepted`，实施细节由 plan 承担；若 G0 失败则改走备选并更新本 ADR。
